吞吐与输出质量 QUALITY

推理吞吐（4 条短 prompt）

⚠ 吞吐 4.6× 差异需谨慎解读

Qwen 输出 489 toks/s 远高于 OPT 106 toks/s，但这不意味 0.6B 比 125M"更高效"。解码吞吐本应随模型变大而下降（显存带宽受限）。真正原因：① OPT 那次运行在推理期触发了 _compute_slot_mapping_kernel 的 一次 Triton JIT 编译尖峰（日志有告警），抬高了计时；② Qwen 走 V2 Model Runner + bf16，kernel 融合更优；③ 样本仅 4 条极短 prompt，结果被固定开销/首 token 延迟主导，非干净的每 token 效率对比。

环境与版本确认 ENV

  • 运行时确认为 v0.22.0：两日志均打印 Initializing a V1 LLM engine (v0.22.0)，且 vllmenv 虚拟环境路径（/slowfs/.../vllmenv/.venv/bin/python → python-3.12.5）印证加载的是已安装的 0.22.0 wheel，与本地 git checkout v0.23.1rc0 源码树不一致（前轮已发现）。
  • 5 个未知环境变量告警：两次运行完全一致（VLLM_SRC 等），属内部构建/CI 变量，无害建议 unset。
  • 权重来源差异：OPT 从 HF Hub 下载（.pt，4.14s）；Qwen 从 NFS 读取 safetensors（1.40 GiB，8 线程预取到 page cache，8.40s 加载），反映集群共享存储布局。
  • V2 Model Runner 仅 Qwen 触发：日志 Using V2 Model Runner（gpu_worker.py:289）只在 Qwen3 出现，OPT 走旧路径 —— 属模型驱动的 runner 选择，非版本差异（同 0.22.0）。
  • Qwen 运行无 Triton JIT 告警：OPT 那次的 _compute_slot_mapping_kernel 推理期编译尖峰在 Qwen 日志中未出现（warmup 覆盖更全 / V2 runner 路径差异）。
