# Agent 开发面试答题稿：失败路径、上下文与不确定性治理

> 触发来源：一条「面试官视角」的短贴（作者：月亮向北），用四个连环问题筛掉只会跑通正常路径的候选人。
> 本文按「出题人真正在测什么 → 每题的 30 秒版 / 深入版 / 追问防御 → 表达模板 → 自测清单」组织，可直接用于面试前复习与临场作答。

---

## 0. 解题总纲

### 0.1 三道判断

1. **这套题不考知识量，考"失败路径的所有权"。** 每一问的句式都是"X 坏了，你的代码做什么"。答"我用了 LangChain / Dify"是零分，答"我有几类失败、每类的确定性动作是什么、最终谁签字"才是分。
2. **"继续追问"是题眼。** 面试官追问，是在验证你第一层回答是背的还是做过的。所以答题必须**自带第二层**：主动交出边界、取舍、代价。
3. **分水岭是"正确性由谁负责"。** 新手把正确性寄托在 prompt 与模型自觉上；上过生产的人把不确定性关进代码的笼子：schema、状态机、预算、幂等、降级、可观测。

### 0.2 答题的固定骨架（五段式）

> **现象** → **怎么定位** → **根因** → **改了什么机制** → **指标变化**

五个要素缺一个就像背的。指标变化是最硬的证据，哪怕是自己项目的离线评测数字。

### 0.3 关于这张贴本身的两个偏误（面试时可点出，属于加分项）

| 贴中表述 | 问题 | 更好的说法 |
|---|---|---|
| "模型是直接调 API，还是先走记忆检索？" | 伪二选一。真实系统两者都要，区别在于**决策由代码还是模型做** | "这是 pre-generation 的**路由**阶段，在代码里判，可测可回归" |
| "这些是线上故障倒逼出来的" | 经验主义偏误。把唯一合法认知来源限定为踩坑 | "失败注入 / 混沌演练 / 轨迹回归集，可以在上线前获得同等认知，而且成本更低" |

## 1. 工具调用稳定性

### 1.1 30 秒版

> "`try-except` 是语法不是策略。我会先把失败分四类：协议层（schema 不符）、下游层（超时/429/5xx）、语义层（200 但业务码错）、系统性（单工具持续失败）。每类对应一个确定性动作——协议层做 field 级 error 回灌让模型自修复，最多两次；下游层做指数退避 + jitter 且**只重试幂等工具**；语义层一律视为失败，绝不喂给模型；系统性走单工具熔断。最后统一收敛到一个失败面，按固定顺序降级：重试 → 缓存 → 安全默认 → 人工 → 明确告知。"

关键动作：**主动说"只重试幂等工具"**。这一句立刻把你和背八股的人区分开，因为它是踩过重复扣款才会有的直觉。

### 1.2 完整版：四类失败面

| 失败类型 | 典型表现 | 确定性动作 | 谁最终负责 |
|---|---|---|---|
| 协议层 | 工具名幻觉、JSON 截断、必填字段缺失、类型错 | 工具 schema 由**函数签名自动生成**（单一真源，禁止手写）；pydantic 校验；把 field 级 error 结构化回灌，最多自修复 2 次 | 代码（校验器） |
| 下游层 | timeout、429、5xx、连接重置 | 分层超时（连接 1s / 读 5s / 单工具总预算）；指数退避 `base × 2^n` + full jitter；仅幂等工具重试 | 代码（重试器 / 守卫） |
| 语义层 | HTTP 200 但 `code != 0`、空集、全 null、单位/币种/时区不对 | 业务码白名单；非 0 一律当失败；**禁止进入上下文** | 代码（校验器） |
| 系统性 | 某工具失败率飙升、下游整体抖动 | per-tool 熔断：窗口内失败率 > 50% → open，30s → half-open 探一次 | 代码（熔断器） |

**降级顺序固定，不允许临场发挥：**

```
重试 → 缓存/上轮值 → 安全默认 → 人工确认 → 明确告知"没拿到，需要你提供 X"
```

最后一级是底线：宁可说不知道，不能让模型编一个"看起来合理"的返回值。**静默编造比报错严重一个数量级**，因为报错触发重试，编造污染整条下游链路。

### 1.3 伪代码

```python
def call_tool(tool, args, ctx) -> ToolResult:
    # ① 协议层：schema 由签名生成，校验在调用前
    try:
        args = tool.schema.validate(args)
    except ValidationError as e:
        return ToolResult.failed("schema_invalid", fields=e.field_errors())  # 回灌自修复

    for attempt in range(MAX_RETRY + 1):
        try:
            with deadline(ctx.budget.remaining):
                raw = tool.invoke(args, idempotency_key=ctx.idem_key)
        except Retryable as e:                 # 429 / 5xx / timeout
            if not tool.idempotent:            # 写操作绝不重试
                return ToolResult.failed(e.cls, e)
            if attempt == MAX_RETRY:
                break
            sleep(backoff(attempt) + random.uniform(0, 0.3))   # full jitter
            continue
        except Fatal as e:
            return ToolResult.failed(e.cls, e)

        # ③ 语义层：HTTP 200 不代表成功
        if not tool.business_ok(raw):
            return ToolResult.failed("business_error", raw.code)
        if is_empty(raw):
            return ToolResult.failed("empty_result", raw)

        # ④ 裁剪：只保留被引用的字段，大结果转句柄
        return ToolResult.ok(trim(raw, tool.keep_fields), handle=ctx.put_blob(raw))
```

```python
@tool                      # schema 从签名自动生成，杜绝手写漂移
def search_orders(user_id: str,
                  since: datetime,
                  status: Literal["paid", "shipped"]) -> list[Order]: ...
```

### 1.4 常被漏掉的一层：可观测性

每次调用必须记：`tool_name / args_hash / latency / error_class / retry_count / degrade_level`。

没有这层，"我做了异常处理"就等于没答——因为你说不出失败率的分母。面试时补一句："我们按 `error_class` 打点，才可能知道 60% 的失败其实是限流而不是超时"，这是"我定位过"的证据。

### 1.5 追问链防御

| 追问 | 应答要点 |
|---|---|
| "重试次数给多少？" | 2~3 次封顶。重试是**放大故障**的工具，下游已经过载时重试是帮凶。配合熔断一起用才有意义 |
| "为什么要 jitter？" | 无 jitter 的同步退避会让所有实例在同一毫秒重试，形成二次雪崩。full jitter 把重试打散到 `[0, backoff]` |
| "写操作怎么重试？" | 先拿 idempotency key（通常由业务主键派生），服务端按键去重；没有幂等保证就**不重试**，转为人工确认 |
| "schema 校验失败回灌，模型会不会一直改不对？" | 会。所以要有次数上限（2 次）+ 错误信息结构化（指明哪个字段、期望什么类型）+ 连续失败就降级成"追问用户" |
| "怎么证明你的降级真的有价值？" | 看 `human_handoff_rate` 和 `invalid_call_rate`，以及降级后答案的**可用率**（用户是否继续追问同一件事） |

## 2. 调用链：路由与结果校验

### 2.1 30 秒版

> "这是伪二选一。真实系统里是**路由**问题：稳定知识直接生成；需要用户私有上下文（偏好、历史决策、任务状态）就先召回再生成；需要外部事实或实时数据就先检索/调工具、拿到证据再生成。关键是**路由在代码里做**，不让模型在 prompt 里自己决定要不要查——后者不可测、不可复现、没法做回归。"

### 2.2 路由的三类信号

```
输入 → [ route 阶段（代码） ]
        ├─ 稳定知识        → 直接生成
        ├─ 用户私有上下文  → 记忆召回 → 生成
        └─ 外部事实/实时   → 工具或检索 → 证据 → 生成
```

判断依据不靠模型：实体类型（订单号/日期/人名）、是否含指代（"上次那个"）、是否涉及易变事实（价格/库存/时效）、是否有明确工具可映射。

### 2.3 工具返回必须校验的三件事

| 维度 | 检查内容 | 失败处理 |
|---|---|---|
| 结构 | schema、字段完整性 | 视为工具失败，走同一失败面 |
| 语义 | 空集、全 null、错误码藏在 body、单位/币种/时区 | 视为失败，**不进上下文** |
| 新鲜度 | `timestamp` / 版本号 / 缓存 TTL | 过期则重取，或显式标注"数据截至 X" |

**外加一条工程常识（第 3 题的伏笔）：裁剪。** 工具返回 50KB JSON 直接塞进上下文，是第 20 轮丢信息的头号凶手。做法：只保留被下游引用的字段；大结果转成"摘要 + 句柄（可再查）"，按需二次取。

## 3. 长对话上下文管理

### 3.1 30 秒版

> "先别谈机制，先谈**怎么定位**。第一步是把第 20 轮的完整 prompt dump 出来，看那条信息还在不在窗口里。在 → 模型侧问题（位置偏中、被冲突信息覆盖、指令优先级不清）；不在 → 工程侧，继续二分是**没写进去**还是**写进去但没召回**：查长期库有没有这条，有就是召回问题，没有就是写入问题。这四步做完，根因唯一确定，不需要猜。"

这题的采分点是**排查路径**，不是名词。上来讲"我用了向量数据库"是最差的开局。

### 3.2 排查树

```
第 20 轮丢失早期关键信息
├─ 1. dump 本轮完整 prompt（trace 必须能逐轮还原）
│   ├─ 信息还在 → 模型侧
│   │   ├─ 位置偏中（lost in the middle）→ 重排到首尾 / pin 进 system 段
│   │   ├─ 被后续冲突信息覆盖 → 显式声明"以下为已确认事实，不得修改"
│   │   └─ 指令优先级不清 → 分层 system / 事实 / 对话，标注不可覆盖
│   └─ 不在 → 工程侧（继续二分）
│       ├─ 查长期库有没有这条
│       │   ├─ 有 → 召回问题：embedding 太弱 / 时间衰减权重过大 / 没 rerank / 没做 query 改写
│       │   └─ 没有 → 写入问题：抽取触发没命中 / 摘要时丢掉 / 只存原文没存结构化槽位
│       └─ 若是窗口塞爆 → 查截断策略
│           └─ FIFO 砍最早 = 典型错误，应按"压缩等级"砍
```

### 3.3 三层记忆 + 压缩等级

| 层 | 内容 | 压缩等级 | 说明 |
|---|---|---|---|
| 工作记忆 | 最近 N 轮原文 | **0（不可压缩）** | 系统指令、硬约束、已确认参数、当前目标常驻 |
| 会话记忆 | 滚动摘要 + 结构化槽位 | 1~2 | 摘要承载叙述，**事实进 state**；寒暄/重复确认可直接丢 |
| 长期记忆 | 向量 + BM25 混合召回 + rerank | — | 关键约束进 pin 集合，每轮无条件注入 |

### 3.4 最关键的一个设计：事实不进摘要

摘要会漂移，而且是单调恶化：

```
第 1 轮：      预算 3000 元
第 5 次摘要： 预算约 3000 元
第 8 次摘要： 预算充足
```

所以：**摘要只承载叙述，事实一律抽成结构化槽位（key-value / JSON state），且 state 不允许被摘要改写。**

```python
state = {
    "budget_cny": 3000,          # 数字原始值，不加工
    "no_color": "red",           # 硬约束
    "deadline": "2026-11-01",
    "confirmed": ["收货地址已确认"],
}
summary = "用户希望在下月初前完成采购，对配色有明确偏好…"   # 只放叙述
```

### 3.5 召回：不要指望相似度撞上硬约束

向量检索对**数字、ID、日期**极不敏感。"用户说过不要用红色"这种约束，靠 embedding 相似度是撞不上的。必须：

1. 向量 + BM25 混合召回（关键词命中兜住精确串）
2. rerank 重排
3. **强制 pin 集合**：把"曾明确说过的约束"打标，每轮无条件注入，不走检索

### 3.6 怎么证明"第 20 轮不丢信息"

可自动化的回归：在**第 1 轮**埋一条约束（"预算 3000，不要红色"），在第 5/10/20/30 轮各问一次，统计 `context_retention@k`。这条能进 CI，是比"我感觉挺稳的"强得多的证据。

### 3.7 追问链防御

| 追问 | 应答要点 |
|---|---|
| "为什么不用超长上下文模型直接硬塞？" | 成本、延迟、注意力稀释（lost in the middle）三重代价；且长上下文不解决**跨会话**记忆，也不解决同一事实被后续对话覆盖的问题 |
| "摘要怎么保证不丢关键信息？" | 不保证。所以关键信息不靠摘要——抽成槽位 + 打压缩等级 0；压缩后可校验关键实体是否还在（自动回归） |
| "多用户/多任务怎么隔离？" | 记忆按 `(user_id, task_id)` 分区；task 结束做一次"归档 + 摘要下沉"，避免不同任务的事实互相污染 |
| "记忆写入的触发条件？" | 不靠模型每轮自问"要不要记"（噪声大），用规则触发：出现数字/日期/否定/偏好句式/明确指令时抽取；抽取后做去重与冲突检测 |

## 4. 不确定性与死循环

### 4.1 30 秒版

> "原则是：不要在 prompt 里求模型别跑偏，要在系统里保证**跑偏了也不会造成后果**。四道护栏按性价比排：预算（步数/工具调用/token/金额）到顶强制收敛；循环检测按 `(tool_name, args_hash)` 计数，同参第二次就把上次结果回给模型并提示换策略，第三次直接拦截交回控制权；计划-执行分离，偏离必须显式 replan；写操作一律幂等 + dry-run + 人工确认。"

### 4.2 四道护栏

| 护栏 | 实现 | 触发时的行为 |
|---|---|---|
| 预算 | `max_steps`、`max_tool_calls`、token/$ 上限 | 强制收敛：输出"当前最优答案 + 未完成事项 + 建议下一步" |
| 循环检测 | `(tool_name, normalized_args)` 做 hash 计数 | 第 2 次：回灌上次结果 + "已调用过，请换策略"；第 3 次：拦截，交回控制权 |
| 计划-执行分离 | 先出结构化 plan（可校验），执行按节点推进 | 偏离需显式 replan 并记录理由，replan 次数也计入预算 |
| 副作用隔离 | idempotency key + dry-run + HITL + 可回滚 | 不确定时让它**提议**而不是**执行** |

**循环检测比任何 prompt 都有效**，因为它不依赖模型自觉：

```python
key = (call.name, hash_args(call.args))   # args 需归一化：去空白、排序 key、统一单位
ctx.call_count[key] = ctx.call_count.get(key, 0) + 1
n = ctx.call_count[key]
if n == 2:
    return f"[duplicate] 你已用相同参数调用过 {call.name}，结果如上，请换策略或基于此作答"
if n >= 3:
    raise LoopDetected(call.name)         # 中断，转总结或反问用户
```

### 4.3 评估：看轨迹，不看单点

| 指标 | 含义 | 目标方向 |
|---|---|---|
| `steps_per_task` | 平均步数 | ↓ |
| `invalid_call_rate` | schema 或语义失败的调用占比 | ↓ |
| `loop_rate` | 触发重复调用的任务占比 | ↓ |
| `tool_selection_acc` | 选对工具的比例 | ↑ |
| `context_retention@k` | 第 k 轮仍能召回首轮约束 | ↑ |
| `human_handoff_rate` | 转人工比例 | ↓ 但有下限 |

线上跑偏的轨迹要落库，作为**回归集**。这才是"生产验证过"的硬证据——比"我踩过坑"更能证明工程素养。

## 5. 高频追问速查

| 追问 | 一句话应答 |
|---|---|
| 模型并行调多个工具，部分失败怎么办？ | 按 `required` 分级：非关键工具失败可继续，关键工具失败终止并降级；结果带 `partial: true` 标记，让模型知道哪块缺 |
| 工具数量多到几十个，模型选不准？ | 两段式：先用检索/规则把候选集缩到 5~8 个再给模型；工具描述里写"什么时候用"而不是"它是什么" |
| 流式输出下怎么处理中断？ | 副作用与流式解耦：先落执行结果，再流式叙述；用户中断时按已提交的副作用回滚 |
| 怎么防止 prompt 注入借工具外泄数据？ | 工具调用前做参数级鉴权（用户能访问该资源吗），而不是信任模型给的参数；返回做敏感字段脱敏 |
| 成本怎么控？ | 分层模型路由（简单任务小模型）、结果缓存、上下文裁剪、工具结果摘要化；按任务设 $ 预算并在超限时降级 |
| 怎么灰度？ | 新 prompt/新工具走 shadow（只记录不生效）→ 5% → 全量，对比 trajectory 指标而非只看满意度 |
