## 一、面试官在筛什么

手写题有**显性评分点**和**隐性评分点**，很多人只盯着显性的一半。

**显性（算法对不对）**：索引算对、同步加对、结果正确。

**隐性（工程素养，占一半分）**：

| 隐性评分点 | 面试官心里在说 |
|---|---|
| 有没有写边界检查 | 你写的代码在真实尺寸上会不会越界 |
| 有没有加 `__restrict__` | 你懂不懂编译器优化 |
| `__syncthreads()` 的位置对不对、有没有漏 | 你理不理解 block 内并行的时序 |
| 有没有考虑 block/grid 的形状为什么这么选 | 你是不是只会抄模板 |
| 会不会说"这个版本在 N=xx 时实测 xx ms" | 你有没有真的跑过 |
| 有没有留测试/校验的思路 | 你会不会 debug 并行代码 |

**一个实用建议**：写之前先说一句"我按 5 步来：确定并行映射 → 处理边界 → 设计访存 → 加同步 → 说优化空间"。面试官会立刻知道你有方法论，后面写慢了也不会被扣成"不会"。

## 二、通用五步法

```
1. 并行映射   : 谁负责哪个输出元素？（thread → output 的一一对应）
2. 边界与形状 : block 多大？grid 多少？怎么保证不越界？
3. 访存设计   : 每份输入会被读几次？需要进 shared 吗？合并吗？
4. 同步点     : 哪里必须 __syncthreads()？加几次？
5. 优化空间   : 向量化 / 分块 / 减少同步 / 用 shuffle / 用 cp.async
```

第 5 步不用全写完，**说出来**就行——白板时间不够时，"我知道下一步该这么优化"比硬写一个半成品强。

## 三、Vector Add（暖身，但别轻视）

```cpp
__global__ void vectorAdd(const float* __restrict__ a,
                          const float* __restrict__ b,
                          float* __restrict__ c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = blockDim.x * gridDim.x;          // grid-stride loop
    for (; i < n; i += stride)
        c[i] = a[i] + b[i];
}
```

**为什么用 grid-stride loop 而不是"一个线程一个元素"？**

| 方案 | 问题 |
|---|---|
| 一线程一元素，`grid = ceil(n/256)` | block 数随 n 膨胀，launch 与调度开销线性增长；尾部 wave 不均衡 |
| grid-stride | grid 固定为 `SM×k`，一次 launch 处理任意 n；循环体里索引递增，**每次迭代都是合并访问**；便于后续做向量化 |

**必答细节**：
- `n` 用 `int` 在 n > 2³¹ 时溢出，大数组要用 `size_t` 或 `long long`。
- `__restrict__` 让编译器敢把 `c[i]` 的写和 `a[i]`/`b[i]` 的读重排、敢用只读缓存路径。
- 向量化版本（`float4`）要求 n 是 4 的倍数且指针 16B 对齐，通常写成"主体走 float4 + 尾巴单独处理"。

**实测参考（A100, N=2²⁴≈16.7M floats）**：这个 kernel 是**纯访存受限**，理论上限 = `3 × 64 MB / 1555 GB/s ≈ 0.12 ms`。如果实测 0.15 ms 就是 80% 峰值带宽，正常；如果实测 1 ms，说明有 stride 问题或被其他因素拖累。**能报出这个数字的人，面试官会认为你真的跑过。**

## 四、GEMM：本教程的核心

### 4.1 朴素版（先写这个，别一上来就 tiled）

```cpp
// C[M][N] = A[M][K] * B[K][N]，这里取方阵 N×N×N 简化讨论
__global__ void matmulNaive(const float* __restrict__ A,
                            const float* __restrict__ B,
                            float* __restrict__ C, int N) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row >= N || col >= N) return;

    float acc = 0.f;
    for (int k = 0; k < N; ++k)
        acc += A[row * N + k] * B[k * N + col];
    C[row * N + col] = acc;
}
```

**它为什么慢？——把它算出来，这是本题的核心**

设 N = 1024：

| 项 | 计算 | 结果 |
|---|---|---|
| 全局读次数 | 每个输出元素读 `A` 的一行 + `B` 的一列 = 2N 次 → 总 `2N³` | 2.15 × 10⁹ 次 |
| 搬运字节 | × 4 B | **8.6 GB** |
| 搬运时间 @1555 GB/s | 8.6 GB / 1555 GB/s | **≈ 5.5 ms** |
| 计算量 | `2N³` FLOPs | 2.15 GFLOP |
| 计算时间 @19.5 TFLOPS | | **≈ 0.11 ms** |

**结论：朴素版慢了 50 倍，而且是纯粹的访存浪费**——每个元素被读了 N 次，但每次都没复用。

**另外一个致命问题**：`B[k*N + col]`，一个 warp 内 `col` 连续但 `k` 固定，所以 `B` 的读是**合并的**（不错）。真正的浪费是**没有复用**，不是不合并。**很多人在这一步就开始胡扯"bank conflict"，其实朴素版根本没有 shared memory，不会有 bank conflict——这种错误一开口就被识破。**

### 4.2 Tiled 版（大厂必考）

```cpp
#define TILE 32

__global__ void matmulTiled(const float* __restrict__ A,
                            const float* __restrict__ B,
                            float* __restrict__ C, int N) {
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];

    int tx = threadIdx.x, ty = threadIdx.y;
    int row = blockIdx.y * TILE + ty;
    int col = blockIdx.x * TILE + tx;

    float acc = 0.f;
    for (int t = 0; t < N / TILE; ++t) {
        // ① 合并地把 tile 读进 shared：每个线程读 1 个元素，warp 内连续
        As[ty][tx] = A[row * N + t * TILE + tx];
        Bs[ty][tx] = B[(t * TILE + ty) * N + col];
        __syncthreads();                       // ② 等所有人都写完

        // ③ 从 shared 里算（这里全部是广播/无冲突访问）
        #pragma unroll
        for (int k = 0; k < TILE; ++k)
            acc += As[ty][k] * Bs[k][tx];

        __syncthreads();                       // ④ 等所有人都读完，才能覆盖 tile
    }
    if (row < N && col < N) C[row * N + col] = acc;
}
```

**访存账（这是"访存节约了多少倍"的标准答案）**

- 每个 block 负责 `TILE × TILE` 个输出。
- 每个 block 需要 `A` 的 `TILE` 行 × `N` 列 + `B` 的 `N` 行 × `TILE` 列 = `2·TILE·N` 个元素。
- block 数 = `(N/TILE)²` → 总读 = `(N/TILE)² × 2·TILE·N = 2N³ / TILE`。

| | 总读元素数 | N=1024, TILE=32 |
|---|---|---|
| 朴素 | 2N³ | 2.15 × 10⁹ |
| Tiled | 2N³ / TILE | 6.7 × 10⁷ |
| **节约倍数** | **TILE** | **32×** |

对应搬运量：8.6 GB → **268 MB**（0.17 ms）。此时计算时间是 0.11 ms，**访存和计算终于在同一量级**——这才是称得上"能用"的 GEMM。真实的高性能 GEMM 用 128×128 的 block tile + 每线程 8×8 寄存器 tile，把访存再降一个数量级，逼近纯计算时间。

**为什么需要两次 `__syncthreads()`？**（这题几乎必问）

- 第一次（写完 tile 之后）：防止有的线程还在写 `As`，别的线程已经开始读 → 读到旧值。
- 第二次（算完 tile 之后）：防止下一轮迭代写 `As` 时，还有线程在算上一轮 → **覆盖未读完的数据**。

**只写第一个是新手最典型的错误**，而且只在 `N/TILE > 1` 时出错（N=TILE 时恰好不出错，测试时容易漏掉），属于"面试官就等你踩"的坑。

**这个版本有 bank conflict 吗？**

没有。逐个看：
- `As[ty][k]`：warp 内 `ty` 固定、`tx` 变化 → **所有线程读同一个地址 → 广播**，1 周期。
- `Bs[k][tx]`：`tx = 0..31` → `bank = tx % 32`，**32 个线程铺满 32 个 bank**，无冲突。
- 写 `As[ty][tx]` / `Bs[ty][tx]`：同样是 `tx` 连续，无冲突。

**所以经典 tiled GEMM 不需要 padding。** 很多人不加分析就给 `[TILE][TILE]` 加 1，反而浪费 shared memory 并破坏向量化——这是一个绝佳的"反向加分项"，你要主动说出来："这里不需要 padding，因为访问模式是广播 + 连续。"

**进阶优化（说出来即可，不要求写完）**
1. **寄存器分块（register tiling）**：每线程算 8×8 个输出，`As`/`Bs` 的 shared 读次数降 8 倍，算术强度大幅提升。这是 cuBLAS 的核心手法。
2. **向量化 shared 访问**：用 `float4` 读 `As` 的一行，把 4 次 shared 读合并成 1 次。
3. **`cp.async` 双缓冲**：算 tile t 的同时预取 tile t+1，把访存延迟藏起来（Ampere）。
4. **swizzle 布局**防冲突（代替 padding，不浪费空间）。
5. 用 `mma.sync` 走 Tensor Core（这是 AI Infra 岗位的加分项）。

## 五、Reduction（并行规约）

### 5.1 从最朴素到最优，四个版本

```cpp
// V0：交错寻址，避免 warp divergence —— 最基础的版本
__global__ void reduce0(const float* in, float* out, int n) {
    extern __shared__ float s[];
    int tid = threadIdx.x;
    int i = blockIdx.x * blockDim.x + tid;
    s[tid] = (i < n) ? in[i] : 0.f;      // ← 边界在这里处理，加载时就归零
    __syncthreads();
    for (int stride = 1; stride < blockDim.x; stride *= 2) {
        if (tid % (2 * stride) == 0) s[tid] += s[tid + stride];
        __syncthreads();
    }
    if (tid == 0) out[blockIdx.x] = s[0];
}
```

**V0 的两个问题（面试常考）**：
1. `tid % (2*stride) == 0` 会导致**严重的 warp divergence**：stride 很小时，一个 warp 里只有少数线程干活，其余 31 条 lane 空转。修复办法是**改成连续寻址**（`s[tid] += s[tid + stride]`，且只让 `tid < stride` 的线程参与），这样活跃线程总是**连续的低编号线程**，warp 被完整使用。
2. 每轮都要 `__syncthreads()`，第一轮之后**只剩 1 个 warp 有活干**，却还在做全 block 同步。

```cpp
// V1：连续寻址（消除 divergence 的主体）
for (int stride = blockDim.x / 2; stride > 0; stride >>= 1) {
    if (tid < stride) s[tid] += s[tid + stride];
    __syncthreads();
}
```

```cpp
// V2：加载时先做一次加法，省掉一整轮（blockDim 减半的思路）
// 每线程负责两个元素，边加载边相加
s[tid] = in[i] + in[i + blockDim.x];    // 注意边界处理
```

```cpp
// V3：最后 32 个元素用一个 warp 搞定，用 shuffle 替代 shared + syncthreads
__inline__ __device__ float warpReduceSum(float v) {
    #pragma unroll
    for (int offset = 16; offset > 0; offset >>= 1)
        v += __shfl_down_sync(0xffffffffu, v, offset);
    return v;
}

__global__ void reduceFinal(const float* __restrict__ in,
                            float* __restrict__ out, int n) {
    float sum = 0.f;
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n;
         i += blockDim.x * gridDim.x)
        sum += in[i];                                  // grid-stride 累加

    sum = warpReduceSum(sum);                          // ① warp 内归约
    __shared__ float s[32];
    int lane = threadIdx.x & 31, wid = threadIdx.x >> 5;
    if (lane == 0) s[wid] = sum;                       // ② 每 warp 出一个结果
    __syncthreads();
    int nwarps = blockDim.x >> 5;
    sum = (threadIdx.x < nwarps) ? s[threadIdx.x] : 0.f;
    if (wid == 0) sum = warpReduceSum(sum);            // ③ 第一个 warp 收尾
    if (threadIdx.x == 0) atomicAdd(out, sum);
}
```

**这个版本每一处都是考点**：
- `__shfl_down_sync(0xffffffff, v, offset)`：lane i 取 lane i+offset 的值，`offset` 从 16→1 递减，5 次归约完 32 个值。
- `0xffffffff` 是**参与 mask**，必须是所有活跃线程；sm_70+ 起必须显式传，否则编译报错。
- 中间结果完全在寄存器里，**零 shared memory 访问、零 `__syncthreads()`**。
- 只需要 `32 × 4 = 128 B` 的 shared memory 做 warp 间交接。
- 最后的 `atomicAdd` 每 block 一次，不是每线程一次。

### 5.2 「为什么 shuffle 比 shared memory 好」的标准答法

三点，按重要性排序：

1. **不需要 `__syncthreads()`**：shared memory 版每轮都要全 block 同步，而 shuffle 是 warp 内寄存器交换，**没有屏障开销**，也不会让空闲的 warp 陪着等。
2. **不占 shared memory、不产生 bank 访问**：shared 的读写各算一次 wavefront，还要考虑 bank conflict；shuffle 直接用寄存器堆的 crossbar，2 个周期内完成。
3. **延迟更低、指令更少**：一条 `SHFL.DOWN` 替代"`LDS` + `FADD` + `STS` + `BAR`"四条。

**追问：那为什么还要用 shared memory？**
因为 shuffle **只能在 warp 内**交换（32 个 lane）。跨 warp 的通信必须经过 shared memory 或 global。所以最优实现是**混合**：warp 内 shuffle，warp 间 shared（就是上面 V3 的两级结构）。

### 5.3 数值正确性的坑

浮点加法**不满足结合律**，所以并行归约的结果和串行结果**一定不严格相等**，误差随规模增长。面试时要点出来：
- 测试时用相对误差（如 `1e-5`）比较，不要 `==`。
- 大规模归约（> 10⁷）建议用 `double` 累加，或用 Kahan 求和 / pairwise summation。
- `torch.sum` 与 `numpy.sum` 结果不一致，根因就是这个——这是 AI Infra 岗位的加分回答。

## 六、Prefix Sum / Scan

### 6.1 两种算法，本质区别是 work efficiency

```cpp
// Hillis-Steele：O(n log n) work，O(log n) 步，简单但"浪费"
__global__ void scanHillisSteele(float* out, const float* in, int n) {
    extern __shared__ float s[];
    int tid = threadIdx.x;
    int gid = blockIdx.x * blockDim.x + tid;
    s[tid] = (gid < n) ? in[gid] : 0.f;
    __syncthreads();

    for (int offset = 1; offset < blockDim.x; offset <<= 1) {
        float v = (tid >= offset) ? s[tid - offset] : 0.f;
        __syncthreads();          // 先读
        s[tid] += v;
        __syncthreads();          // 后写 —— 两次同步都不能少
    }
    if (gid < n) out[gid] = s[tid];
}
```

**关键点：为什么循环里要两次 `__syncthreads()`？**
第一轮：所有线程**先读** `s[tid-offset]` 到寄存器；第二轮：再写回 `s[tid]`。如果先写后读，早写的线程会覆盖别人还没读的值——**in-place 原地更新必须"读完再写"**。这个细节是 scan 题的经典考点。

```cpp
// Blelloch：O(n) work，2n 次操作，up-sweep + down-sweep，work-efficient
// 思路：上扫把数组变成"部分和树"，下扫把树还原成前缀和
// 代价是步骤更多（2 log n），但总操作数从 n log n 降到 2n
```

| | Hillis-Steele | Blelloch |
|---|---|---|
| 步数 | log₂n | 2·log₂n |
| 总操作数 | n·log₂n | 2n |
| Work efficiency | O(log n)（不高效） | **O(1)（高效）** |
| 实现难度 | 低 | 中（下扫要处理边界） |
| 适用 | 小数组、GPU 充足并行度 | 大数据、追求总吞吐 |

**面试答法**："GPU 上有海量并行度时，Hillis-Steele 的 log n 步并不亏——因为每步都是满 warp 并行。但当 n 很大、要跨 block 分块扫时，Blelloch 的 work-efficient 特性更重要，因为总工作量决定了要跑多少 SM-周期。工程实现都是**块内 Blelloch + 块间分层扫描（scan-then-propagate）**，CUB 的 `DeviceScan` 就是这么做的。"

### 6.2 Scan 的工程难点（说出来是加分项）

1. **跨 block**：块内扫完只得到"块内前缀"，还要把每块的总和再扫一遍，然后把偏移加回去（三阶段：scan → scan block sums → add offsets）。
2. **原地（in-place）**：两次同步的时序问题（见上）。
3. **非 2 的幂**：要补零到 2 的幂，或者用非平衡树。
4. **decoupled look-back**（CUB 的做法）：单 kernel 内用 flag 做前向依赖，避免三次 kernel 启动。

## 七、Histogram

```cpp
#define BINS 256
__global__ void histogram256(const unsigned char* __restrict__ data, int n,
                             unsigned int* __restrict__ hist) {
    __shared__ unsigned int local[BINS];             // 1 KB / block
    for (int i = threadIdx.x; i < BINS; i += blockDim.x) local[i] = 0;
    __syncthreads();

    int stride = blockDim.x * gridDim.x;
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += stride)
        atomicAdd(&local[data[i]], 1u);              // shared atomic，快

    __syncthreads();
    for (int i = threadIdx.x; i < BINS; i += blockDim.x)
        if (local[i]) atomicAdd(&hist[i], local[i]); // 每 block 每 bin 至多 1 次
}
```

**考点全在这一句**：全局 atomic 从"每元素一次"降到"每 block 每 bin 一次"。10⁸ 个像素、1024 个 block 的情况下，全局原子次数从 10⁸ 降到 1024×256 = 2.6×10⁵，**降了 380 倍**。

**追问：shared atomic 还有竞争怎么办？**
数据分布集中时（比如图像大部分是背景），同一个 bin 会被连续多个线程撞上 → shared atomic 也串行。进一步优化：
- **多副本 bin**（privatization）：每个 warp 一份直方图（32 × 1 KB = 32 KB），最后合并，冲突降为原来的 1/32。
- **warp 级聚合**：`__match_any_sync` 找出同值的 lane，`__popc` 算个数，一个 leader 做一次加法。
- **排序后统计**：先 radix sort 再分段计数，彻底消除冲突（但排序成本高）。

## 八、题库

### Q1. 手写一个基于 shared memory 的矩阵乘法，并说明访存节约多少倍

**答题结构（一定要按这个顺序说）**：
1. 先说朴素版的账：`2N³` 次全局读，N=1024 时 8.6 GB，需要 5.5 ms，而计算只要 0.11 ms → **纯访存受限，慢了 50 倍**。
2. 给出 tiled 代码（见 4.2）。
3. 算账：总读从 `2N³` 降到 `2N³/TILE`，**节约 TILE 倍 = 32 倍**。
4. 补充：为什么两次 `__syncthreads()`；为什么这里不需要 padding（广播 + 连续）。
5. 收尾：真实 GEMM 会再加 register tiling + `cp.async` + Tensor Core。

**追问：TILE 能不能设成 64？** 能，但 shared memory 变成 `2 × 64² × 4 = 32 KB`，A100 的 164 KB 还能放 5 个 block（不过 64×64=4096 线程超了 1024 限制，所以 block 要改成 256 线程、每线程算 4×4 个输出）。TILE 增大的收益是访存再降一半，代价是 shared 压力、occupancy 下降、寄存器压力上升。**经验值：TILE=32 配 256 线程是甜点，128 需要 2 级分块 + 寄存器分块。**

**追问：如果 N 不是 TILE 的整数倍？** 两个办法：① 边界检查 `if (row < N && col < N)` + tile 加载时补 0；② padding 到 TILE 的倍数。**必须在加载 tile 时判边界，否则越界读**。

### Q2. Reduction 最后为什么可以不用 `__syncthreads()`？

**30 秒答法**：当一个 block 的剩余工作量 ≤ 32 个元素时，它正好落在一个 warp 内，可以用 `__shfl_down_sync` 在寄存器之间直接交换，**完全绕过 shared memory**。warp 内的执行是锁步的（配合 `__syncwarp()`），不需要 block 级屏障。所以"最后 32 个元素用一个 warp 收尾"是标准优化。

**追问：Volta 之后 `__syncwarp()` 必须加吗？** 是的。独立线程调度让 warp 内不再有隐式同步保证，shuffle 的 `_sync` 版本本身带同步语义，但如果 warp 内有更复杂的分支，必须显式 `__syncwarp()`。

**追问：`0xffffffff` 这个 mask 能改吗？** 能，但必须是"参与这次 shuffle 的所有 lane"的位掩码。写错会导致结果不确定。常见做法是先用 `__activemask()`，但**官方建议尽量用常量全 1 mask**，因为 `__activemask()` 在分支内不可靠。

### Q3. 为什么归约的第一轮就把边界检查做掉？

**30 秒答法**：因为边界检查如果留到循环里，每轮都要判断 `i < n`，而且会让最后一个 warp divergence。**更好的做法是在加载阶段就把越界元素置 0**（`s[tid] = (i < n) ? in[i] : 0.f`），之后所有线程都按满长度参与规约——加法单位元是 0，不影响结果。这属于"把控制流成本前移到数据准备"的通用手法。

**追问：那 vector add 能不能这么干？** 不能，因为写操作没有单位元。**读可以补零，写必须判边界**——这个区分答出来很漂亮。

---

### Q4. 你写的 reduction 和 `thrust::reduce` 差多少？为什么？

**30 秒答法（诚实版）**：单 block 小规模时我的版本和 thrust 差距在 10% 内；但大规模时 thrust/CUB 明显更快，因为它做了：① **多级归约 + decoupled look-back**，单次 kernel 完成；② **向量化加载（`float4`）**，把访存指令数降到 1/4；③ **针对具体架构调过 block size 和 unroll 因子**；④ 用 `__ldg` 走只读缓存。

**这题的价值不在"我写得比库好"，而在"我知道库为什么好"**——面试官问这个就是筛这个。

### Q5. 手写一个 warp 内的 inclusive scan

```cpp
__device__ float warpScanInclusive(float v) {
    #pragma unroll
    for (int offset = 1; offset < 32; offset <<= 1) {
        float t = __shfl_up_sync(0xffffffffu, v, offset);
        if ((threadIdx.x & 31) >= offset) v += t;
    }
    return v;
}
```
**要点**：`__shfl_up_sync` 取的是"比自己 lane 号小 offset"的值，所以只有 `lane >= offset` 的线程才累加（否则会读到无效值/自己的值）。这是 scan 用 shuffle 实现的唯一正确写法，也是 Hillis-Steele 在 warp 内的等价形式。

### Q6. 面试官让你"再快一点"，你按什么顺序试？

**标准答法（按投入产出比排序）**：
1. **看 NCU 的 SOL**：先确定是 compute bound 还是 memory bound，不要盲猜。
2. 若是 memory bound：向量化访存（`float4`）→ 提高复用（shared/tile）→ 调整 block size 提升 occupancy。
3. 若是 compute bound：减少非必要指令（用 FMA、避免 `pow`/`exp`）→ 提高 ILP（每线程多算几个元素）→ 上 Tensor Core。
4. 若是 latency bound（occupancy 低、stall 高）：加线程/减寄存器压力 → 用 `cp.async` 做流水。
5. 最后才考虑算法级改动。

**这题答"我一般先试加 shared memory"就废了**——因为方向可能是错的。**先测量，再优化**，是这题唯一正确的开场。
