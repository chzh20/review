## 二、并发与异步：Stream

### 2.1 基本模型

CUDA 的执行是异步的：kernel launch 和 `cudaMemcpy` 只是**入队**，主机端立刻返回。真正的执行在 stream（队列）里按序进行。

- **同一个 stream 内：严格保序**（FIFO，不重叠）。
- **不同 stream 之间：可并发**（受资源限制）。
- **默认流（legacy default stream）有个特殊行为**：它会和**所有其他阻塞 stream 同步**——也就是说，你在默认流上做什么，都会等别的 stream 干完。这是"我明明开了多 stream 却没重叠"的最常见原因。

**解决办法**：编译时加 `--default-stream per-thread`，让默认流变成每线程独立；或者干脆**全程显式用非默认 stream**（推荐）。

### 2.2 计算与传输重叠的标准写法

```cpp
cudaStream_t s[2];
for (int i = 0; i < 2; ++i) cudaStreamCreate(&s[i]);

float *h; cudaMallocHost(&h, 2 * BYTES);      // ← 必须是 pinned memory
float *d; cudaMalloc(&d, 2 * BYTES);

for (int b = 0; b < nblocks; ++b) {
    int cur = b % 2;
    cudaMemcpyAsync(d + cur * N, h + cur * N, BYTES,
                    cudaMemcpyHostToDevice, s[cur]);   // 传输
    kernel<<<grid, block, 0, s[cur]>>>(d + cur * N);   // 计算
    cudaMemcpyAsync(h + cur * N, d + cur * N, BYTES,
                    cudaMemcpyDeviceToHost, s[cur]);   // 回传
}
```

**三个必须同时满足的条件**（缺一个就没有重叠，这是面试的标准答案）：
1. 用 **`cudaMallocHost` 分配的页锁定内存**。普通 `malloc` 的内存 `cudaMemcpyAsync` 会退化成"经由内部 bounce buffer 的同步拷贝"，因为它不能被 DMA 直接访问。
2. 用**不同的 stream**，且没有默认流介入。
3. 设备有**足够的资源**同时跑两个 kernel（SM、寄存器、shared memory 都够）。

**实测验证方法**：用 `nsys profile -t cuda,nvtx` 看时间线，Memcpy 和 Kernel 的色块如果在横轴上有重叠，才算真的重叠了 [R6]。

### 2.3 计时：不要用 CPU 计时器

```cpp
cudaEvent_t start, stop;
cudaEventCreate(&start); cudaEventCreate(&stop);
cudaEventRecord(start);
for (int i = 0; i < iters; ++i) kernel<<<...>>>(...);
cudaEventRecord(stop);
cudaEventSynchronize(stop);
float ms; cudaEventElapsedTime(&ms, start, stop);
```

**要点**：
- 先用几次 warm-up 把 GPU 频率拉起来（GPU 有 DVFS，冷启动那次会明显慢）。
- 多次迭代取平均，单次测量噪声很大。
- `cudaEventElapsedTime` 的分辨率约 0.5 μs，测 < 10 μs 的 kernel 要放大迭代次数。

## 三、性能分析：Nsight Compute 与 Nsight Systems

### 3.1 两个工具的分工（这题必考）

| | Nsight Systems (`nsys`) | Nsight Compute (`ncu`) |
|---|---|---|
| 层级 | **系统级 / 时间线** | **单个 kernel 内部** |
| 回答什么 | 谁在等谁、传输和计算重叠了吗、哪个 kernel 最耗时 | 这个 kernel 为什么慢、瓶颈在哪个单元 |
| 开销 | 低（可用于生产 profile） | 高（要 replay kernel 多遍） |
| 典型用法 | `nsys profile -t cuda,nvtx ./app` | `ncu --set full ./app` |

**一句话答法**："先用 nsys 找瓶颈在哪，再用 ncu 分析那个 kernel 为什么慢。"

### 3.2 SOL 页面：这是 W4 最重要的工具

`SpeedOfLight` 章节给的是**相对理论峰值的利用率**：每个单元的实际吞吐 / 该单元的理论最大吞吐 [R5]。

```
Compute (SM) Throughput   : 87.3 %     ← 逼近 100% 说明计算单元是瓶颈
Memory Throughput         : 21.5 %     ← DRAM 还有余量
DRAM Throughput           : 20.1 %
L1/TEX Throughput         : 45.2 %
Duration                  : 1.23 ms
```

**判读规则（面试要能张口说）**：

| 现象 | 结论 | 下一步 |
|---|---|---|
| Compute 高（>80%），Memory 低 | **计算受限** | 减少指令数 / 提 ILP / 上 Tensor Core |
| Memory 高（>80%），Compute 低 | **访存受限** | 提高复用、合并访存、减小数据量 |
| 两者都低（<50%） | **延迟受限 / 并行度不足** | 加 occupancy、减同步、加 ILP、查 stall reason |
| 两者都高 | 已经接近机器平衡点，很难再快 | 换算法（如用 Tensor Core 提高峰值） |

**关键指标名**（版本不同名字略有差异，用 `ncu --query-metrics` 查当前版本）：

| 指标 | 含义 |
|---|---|
| `sm__throughput.avg.pct_of_peak_sustained_elapsed` | Compute 吞吐利用率 |
| `gpu__dram_throughput.avg.pct_of_peak_sustained_elapsed` | DRAM 带宽利用率 |
| `sm__warps_active.avg.pct_of_peak_sustained_active` | **Achieved Occupancy** |
| `l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum` | 全局 load 的 sector 数（判断合并） |
| `smsp__average_warps_issue_stalled_long_scoreboard_per_issue_active.ratio` | 等内存导致的 stall 占比 |
| `sm__maximum_warps_per_active_cycle_pct` | 理论 occupancy 上限 |

**"Waves Per SM" 是被低估的指标**：`LaunchStats` 里如果显示 `Waves Per SM = 1.03`，说明你的 grid 只比 SM 数多一点点，最后 0.03 波会浪费大量时间（典型 tail effect）。修法：调整 block 数使其成为整数波，或改用 grid-stride。

### 3.3 分析流程（面试可背的 4 步）

1. **看 Duration，确认值得优化**（别优化 0.5% 的 kernel）。
2. **看 SOL**，定位 compute / memory / latency。
3. **看 Memory Workload Analysis**（如果是 memory bound）：L1/L2 命中率、sector 数/请求数（>4 说明没合并好）、bank conflict 计数。
4. **看 Warp State Stats / Scheduler Stats**（如果是 latency bound）：stall 原因分布，最典型的是 `long scoreboard`（等 global memory）和 `barrier`（等同步）。

## 四、Roofline：判断瓶颈的理论工具

Roofline 模型 [R12]：

```
可达到性能 = min(峰值算力, 算术强度 × 峰值带宽)

算术强度 AI = FLOPs / Bytes（每从 HBM 搬 1 字节，能算多少次浮点运算）
```

**A100 的两条"屋脊"**（这个数字面试时要能直接报）：

| 精度 | 峰值 | 平衡点 AI |
|---|---|---|
| FP32 | 19.5 TFLOPS | 19.5e12 / 1555e9 ≈ **12.5 FLOP/B** |
| TF32 Tensor | 156 TFLOPS | ≈ **100 FLOP/B** |
| FP16/BF16 Tensor | 312 TFLOPS | ≈ **200 FLOP/B** |

**推论（这是最重要的一段）**：

- vector add：`2 FLOP / 12 B` = 0.17 FLOP/B → **远远在屋脊左边，纯访存受限**，任何"优化计算"的努力都是白费。
- GEMM 朴素版：`2N³ FLOP / (2N³ × 4 B)` = 0.25 FLOP/B → 也是访存受限（因为没复用）。tiled 后 AI 提升 TILE 倍 → 8 FLOP/B，还是 FP32 的左坡；用 Tensor Core + 128 分块才能到 200 以上。
- Attention（标准实现）：AI 很低（N×N 矩阵反复进出 HBM）→ 访存受限 → **这正是 FlashAttention 的出发点**。

**为什么"上 Tensor Core 就一定快"是错的**：如果你的 kernel AI 只有 5 FLOP/B，换到 200 FLOP/B 的 Tensor Core 上，你还是卡在带宽上，一点都不会快。**先提 AI，再换硬件单元。**

## 五、FlashAttention：本节的唯一重点

### 5.1 标准 Attention 的问题

```
S = Q·Kᵀ        (N×N，写 HBM)
P = softmax(S)  (N×N，读 S 再写 P)
O = P·V         (读 P)
```

对 `N=4096, d=64, FP16`：`S` 和 `P` 各占 `4096² × 2 B = 32 MB`。**它们都要完整地写进 HBM 再读回来**——但每一块 SRAM 只有 192 KB。

论文给出的 IO 复杂度 [R8]：

| 实现 | HBM 访问次数 | 额外显存 |
|---|---|---|
| 标准 Attention | `Θ(Nd + N²)` | `Θ(N²)` |
| **FlashAttention** | **`Θ(N²d²/M)`**（M 为 SRAM 大小） | **`Θ(N)`** |

当 `M ≫ d²` 时，FlashAttention 的 HBM 访问比标准实现少一个数量级。**它没有减少 FLOPs（甚至因为重算而略增），减少的是 HBM 读写。**

> **面试必须说清的一句话**：FlashAttention **不是近似算法**，输出与标准 attention **完全一致**（exact attention）。它优化的是 **IO**，不是数学。

### 5.2 核心机制一：Tiling + Online Softmax

不能把整个 N×N 矩阵放进 SRAM，所以按行块 `Q_i`（大小 `B_r × d`）和列块 `K_j, V_j`（`B_c × d`）迭代：

```
对每个 row block i:
    O_i = 0,  l_i = 0,  m_i = -∞        # 累加器、softmax 分母、运行最大值
    对每个 col block j:
        S_ij = Q_i · K_jᵀ                # 只存在于 SRAM
        m_new = max(m_i, rowmax(S_ij))   # 新的运行最大值
        P_ij  = exp(S_ij - m_new)        # 用新 max 归一化
        l_new = exp(m_i - m_new) * l_i + rowsum(P_ij)
        O_i   = exp(m_i - m_new) * O_i + P_ij · V_j   # ← 关键：旧的 O_i 要乘修正因子
        更新 m_i = m_new, l_i = l_new
    O_i = O_i / l_i                       # 最后才除
```

**这三行（`m`、`l`、`O` 的更新）就是 online softmax，是整道题的核心。** 为什么可以这样？因为 softmax 的数值稳定性靠"减去最大值"，而最大值可以**增量更新**：新块带来的最大值变大时，只需把**之前累加的结果乘一个指数修正因子**重新缩放，就能得到与"一次性看到全部数据"完全相同的结果。

**追问：为什么不能先算 `exp(S_ij)` 再累加？** 因为 `exp` 的值会溢出（`S` 的数值范围可达 ±100，`exp(100)` 在 FP16 里直接变 inf）。必须先减去当前最大值。而"最大值"是流式到达的，所以必须做增量修正。

**追问：除法 `O_i / l_i` 放在哪里？** 放在最外层循环结束后，**一次**。FA1 里每个 tile 都除一次（多余的非矩阵乘 FLOPs），FA2 把它推迟到外层——这是 FA2 的主要优化之一 [R9]。

### 5.3 核心机制二：Backward 重算（recomputation）

前向只保存 `O` 和 softmax 的统计量 `(m, l)`，**不保存 N×N 的 `P`**。反向传播需要 `P` 时，用 `Q, K` 在 tile 内**重新算一遍** `S` 和 `P`。

- 代价：多一次 `QKᵀ` 的 FLOPs（前向的 ~1/3 额外计算）。
- 收益：显存从 `Θ(N²)` 降到 `Θ(N)`，HBM 读写大幅减少。

**为什么"多算反而更快"？** 因为 A100 上 FP16 Tensor 的算力是 312 TFLOPS，而带宽只有 1555 GB/s——**算一次 FLOP 比从 HBM 搬一个字节还便宜**（200 FLOP 换 1 字节的平衡点）。这就是 IO-aware 优化的经济学基础。这句话是本题的"高分句"。

### 5.4 FA1 / FA2 / FA3 的演进（答出来是加分项）

| 版本 | 关键改进 |
|---|---|
| FA1 (2022) | Tiling + online softmax + recomputation，首次把 attention 从 memory bound 拉向 compute bound |
| FA2 (2023) | ① 减少 non-matmul FLOPs（延迟 rescale、不在每个 tile 除）；② **在 sequence 维度并行**（FA1 只在 batch×head 上并行，长序列小 batch 时 GPU 吃不满）；③ warp 级工作划分，减少 shared memory 通信 [R9] |
| FA3 (2024) | 面向 Hopper：**WGMMA（warpgroup MMA）+ TMA 异步**，把 softmax 与 GEMM 流水起来；支持 **FP8**；针对 FP8 的低精度做 softmax 的特殊处理 [R10] |

### 5.5 「讲一讲 FlashAttention 的原理，它为什么能变快」

**60 秒标准答案模板**：

> "标准 attention 要把 N×N 的注意力矩阵完整写进 HBM 再读回来，显存和带宽都是 Θ(N²)，这是典型的 memory bound。FlashAttention 用两个手段解决：一是 **tiling**，把 Q/K/V 切成块，让每个 `B_r×B_c` 的分数块只在 SRAM 里算完就丢掉，配合 **online softmax** 用运行最大值 `m` 和分母 `l` 增量更新，最后才做一次除法，结果与标准实现**完全等价**；二是**反向重算**，只存 O 和 (m,l)，不存 P，需要时用 Q/K 重新算，显存从 Θ(N²) 降到 Θ(N)。所以它的 HBM 访问从 Θ(Nd+N²) 降到 Θ(N²d²/M)。**它不减 FLOPs，反而多算了一点，但因为省下的是带宽，而 A100 上 1 字节的搬运成本相当于 200 次 FP16 FLOP，所以净收益是 2–4 倍的实际加速。**"

**追问：那 attention 的瓶颈到底是什么？** 长序列时是 HBM 带宽；短序列时是 kernel launch 和并行度不足。FlashAttention 在 seq < 512 时收益有限，这也是为什么 FA2 要加 sequence 并行。

**追问：为什么现在的推理引擎都默认用它？** 因为它同时降显存和降带宽，长上下文场景（32K+）下显存从 O(N²) 变 O(N) 是**能不能跑**的区别，不只是快慢。

## 六、混合精度与 Tensor Core

### 6.1 四种格式的差别（表格要能默写）

| 格式 | 位分配（符号/指数/尾数） | 可表示范围 | 精度 | 用途 |
|---|---|---|---|---|
| FP32 | 1 / 8 / 23 | ±3.4×10³⁸ | 24 bit 有效 | 基准、累加 |
| **TF32** | 1 / 8 / 10 | 同 FP32 | 11 bit 有效 | Tensor Core 吃 FP32 输入时自动用 |
| **FP16** | 1 / 5 / 10 | **最大 65504**，最小正规数 6.1×10⁻⁵ | 11 bit 有效 | 训练/推理主力 [R14] |
| **BF16** | 1 / 8 / 7 | **与 FP32 同范围** | 8 bit 有效 | 大模型训练首选（不用 loss scaling） |
| **FP8 E4M3** | 1 / 4 / 3 | 最大 448 | 4 bit 有效 | Hopper 推理/训练，需 per-tensor scaling |
| **FP8 E5M2** | 1 / 5 / 2 | 最大 57344 | 3 bit 有效 | 梯度场景（范围优先） |

**核心区别一句话**：**FP16 精度高但范围窄，BF16 范围大但精度低**。深度学习对"范围"的敏感度远高于"精度"（梯度可能小到 1e-8），所以大模型训练几乎都用 BF16。

### 6.2 Loss Scaling 为什么必需

FP16 的最小正规数是 `6.1×10⁻⁵`，小于它的梯度会**下溢成 0**，训练直接卡死 [R14]。

解法：前向算完 loss 后乘以一个缩放因子 `S`，链式法则让所有梯度同步放大 `S` 倍，反传后再除以 `S`。

- **静态缩放**：取 8 ~ 32768，原则是"最大梯度 × S < 65504"（不溢出）。
- **动态缩放**：从大值开始，连续 N 步（如 2000）没溢出就 ×2，一旦出现 inf/NaN 就 ×0.5 并**跳过这次权重更新**。

**追问：BF16 需要 loss scaling 吗？** 不需要，它的指数范围和 FP32 一样（8 位）。这就是它在大模型训练里取代 FP16 的原因。

### 6.3 Tensor Core 的约束

- 指令是 **warp 级**的（不是线程级）：`mma.sync.aligned.m16n8k16` 表示一个 warp 的 32 个线程协作完成 16×8 输出、K=16 的矩阵乘。
- Ampere 常见形状：FP16/BF16 `m16n8k16`，TF32 `m16n8k8`，INT8 `m16n8k32`。
- 累加器在寄存器里，FP16 输入可以 FP32 累加——**累加一定要用 FP32**，否则大 K 时误差爆炸。
- 数据布局有要求（`ldmatrix` 指令专门负责把 shared memory 的数据搬成 Tensor Core 需要的 fragment 布局）。

**面试延伸**："为什么矩阵维度要 pad 到 8 的倍数？"因为 Tensor Core 的 tile 形状是固定的，K 不能被 16/8 整除时尾部要补零，否则要么算错要么退化到 CUDA core 路径。

## 七、从 CUDA 到推理引擎：面试的延伸战场

如果目标是 AI Infra / 推理引擎岗，W4 之后必然被问到这一层。三个必须会的点：

### 7.1 Prefill 与 Decode 的瓶颈完全不同

| 阶段 | 计算特征 | 瓶颈 | 优化方向 |
|---|---|---|---|
| **Prefill**（处理 prompt） | 大矩阵乘，batch 大，AI 高 | **compute bound** | Tensor Core、FlashAttention、算子融合 |
| **Decode**（逐 token 生成） | 每步只算 1 个 token，要读全部权重 | **memory bound**（读权重） | KV cache、量化、continuous batching |

**一句话**："decode 阶段每生成一个 token 都要把模型权重从 HBM 读一遍，所以是纯带宽受限——这就是量化和 KV cache 优化的全部动机。"

### 7.2 KV Cache 的显存账（能算就是加分）

```
KV cache 字节数 = 2(K和V) × layers × kv_heads × head_dim × seq_len × batch × dtype_bytes
```

以 LLaMA-2-7B 为例：32 层、32 头、head_dim 128、FP16、seq 4096、batch 1：
`2 × 32 × 32 × 128 × 4096 × 2 ≈ 2.1 GB` —— **比模型权重（13 GB）小，但随 batch 和 seq 线性爆炸**。batch=32、seq=8192 时就是 34 GB，直接超显存。所以有了 MQA/GQA（减少 kv_heads）和 PagedAttention（消除碎片）。

### 7.3 PagedAttention 解决的是什么

传统 KV cache 要求**连续显存**，按最大长度预分配 → 内部碎片（实际用的远少于分配的）和外部碎片。PagedAttention 借操作系统的分页思想：把 KV cache 切成固定大小的 block，用 block table 做逻辑到物理的映射，**按需分配**。收益是显存利用率从 ~60% 提到 >90%，从而能塞更大的 batch。

**这题和 CUDA 的关系**：它本身不需要写 kernel，但它决定了 kernel 的访存 pattern（gather 式的 block table 查表）——面试官问"这个 gather 会不会导致不合并访存"，就回到 W2 了。

## 八、题库

### Q1. 如何判断一个 CUDA 程序是计算密集型还是访存密集型？

**30 秒答法**：两个层次。**理论上**算算术强度 `AI = FLOPs / Bytes`，和机器的平衡点比：A100 FP32 是 12.5 FLOP/B，FP16 Tensor 是 200 FLOP/B，`AI <` 平衡点就是访存受限。**实测上**看 NCU 的 SOL 页面，Compute 和 Memory 哪个接近 100%。

**追问：算不出来 FLOPs 怎么办？** 用 NCU 直接看，它会帮你算 `Arithmetic Intensity` 并画在 Roofline 图上（`SpeedOfLight_RooflineChart` 章节）。

**追问：为什么同一个 kernel 在 A100 和 H100 上可能从 compute bound 变成 memory bound？** 因为两者的"算力/带宽"比不同。H100 SXM 是 67 TFLOPS FP32 / 3.35 TB/s ≈ 20 FLOP/B，比 A100 的 12.5 更高，所以同样的 kernel 在 H100 上更容易变成访存受限。**"平衡点会随硬件漂移"是这道题的高分点。**

---

### Q2. 给你一个耗时很长的 Kernel，用 NCU 分析时优先看哪几个指标？

**30 秒答法**：按顺序看四个：
1. **SOL 的 Compute / Memory Throughput** —— 先定性瓶颈类型；
2. **Achieved Occupancy + Waves Per SM** —— 并行度够不够、有没有 tail effect；
3. **Memory Workload Analysis 的 sectors per request** —— 大于 4 说明访存没合并（理想是 4，对应 128B / 32B）；
4. **Warp State Stats 的 stall 原因** —— `long scoreboard` 是等内存，`barrier` 是同步太多，`MIO throttle` 是 shared 访存压力大。

**追问：`sectors per request` 理想值为什么是 4？** 一条 128 B 的 cache line = 4 个 32 B sector。一个 warp 的 32 个 float 正好铺满 4 个 sector。超过 4 就说明有跨行/跨步，效率下降。

**追问：如果 Occupancy 只有 25%，但 SOL 显示 Compute 90%，要优化吗？** 不用。这说明 ILP 足够，少的 warp 也能把流水线填满（GEMM 就是这样）。**低 occupancy 不等于慢**，这是必须能说清的反例。

---

### Q3. Stream 用了，为什么没有重叠？

**30 秒答法**：三个常见原因。① 用了**默认流**，它会和所有阻塞流同步；② 内存不是 **pinned memory**，`cudaMemcpyAsync` 退化成同步；③ 前后操作有**数据依赖**且在同一个 stream 里（同 stream 严格保序）。

**追问：怎么验证重叠发生了？** `nsys profile -t cuda` 看时间线，Memcpy 和 Kernel 的色块在时间轴上重叠才是真重叠。只看总时间变短不够（可能是频率波动）。

**追问：多 stream 并发 kernel 有什么前提？** 资源要够（SM、寄存器、shared memory）。如果第一个 kernel 就把 108 个 SM 占满，第二个只能排队——**并发是资源允许时的机会，不是保证**。

---

### Q4. `cudaMemcpy` 和 `cudaMemcpyAsync` 的区别？什么时候前者更快？

**30 秒答法**：`cudaMemcpy` 是同步的，会阻塞主机线程直到完成；`cudaMemcpyAsync` 只是入队，必须配 pinned memory 才能真异步。**如果只有一次传输且之后立刻要等结果，两者差不多**——同步版本内部会做优化（比如用小 kernel 搬数据）。异步的收益只在"能和其他工作重叠"时才体现。

**追问：pinned memory 为什么快？** 页锁定内存不会被操作系统换出，GPU 的 DMA 引擎可以直接访问，不需要 CPU 参与中介。代价是分配慢、占用物理内存、过度使用会拖慢整个系统。

---

### Q5. 讲一讲 FlashAttention 的原理，它为什么能变快？

见 5.5 的 60 秒模板。**这题一定要背到能一口气说完。**

**高频追问清单**：
- 它是近似算法吗？→ **不是，exact**。
- 它省的是什么？→ **HBM 读写，不是 FLOPs**（FLOPs 反而略增）。
- online softmax 怎么保证数值稳定？→ 运行最大值 `m` 增量更新 + 指数修正因子重缩放累加器。
- 反向怎么省显存？→ 只存 O 和 (m,l)，P 用 Q/K 重算。
- FA2 比 FA1 好在哪？→ 减少 non-matmul FLOPs + sequence 维度并行 + 更好的 warp 划分。
- 什么情况下 FlashAttention 没有明显收益？→ 序列很短（<512）、或者已经 compute bound 的大 batch prefill。

---

### Q6. FP16 训练为什么要 loss scaling，BF16 为什么不用？

**30 秒答法**：FP16 只有 5 位指数，最小正规数 6.1e-5，梯度很容易下溢成 0，所以要乘一个缩放因子把梯度拉到可表示范围，反传后再除回来。BF16 有 8 位指数，和 FP32 同范围，只是尾数少（7 位），精度差但不溢出，所以不需要 scaling。

**追问：那 BF16 的精度损失怎么办？** 靠 FP32 累加。Tensor Core 的累加器是 FP32，所以矩阵乘的中间结果不会丢精度，只有输入被截断。

**追问：FP8 呢？** 范围更小（E4M3 最大 448），需要 per-tensor 或 per-block 的 scaling factor，而且 softmax 这类对精度敏感的操作要用特殊处理（FA3 里有专门讨论）[R10]。

---

### Q7. 你的 kernel 比 cuBLAS 慢 5 倍，你怎么追？

**30 秒答法**：先不追，先量化。① 用 NCU 对比两者的 SOL，看是 compute 差还是 memory 差；② 如果 memory 差，看 sectors per request 和 L2 命中率；③ 如果 compute 差，看指令数和 Tensor Core 利用率；④ 大概率会发现差距在 **register tiling 的粒度**（cuBLAS 每线程算 8×8）和 **`cp.async` 流水**上。

**这题的价值**：面试官不是要你超过 cuBLAS，是要你**有方法论**。承认"追不上是正常的"反而加分——cuBLAS 有专门的团队和架构级调优。

---

### Q8. 什么是 "waves per SM"，为什么它重要？

**30 秒答法**：`grid 的 block 总数 / 每 SM 能同时容纳的 block 数 / SM 数`，即"要几波才能跑完"。如果是 1.05 波，意味着第二波只有 5% 的 block 在跑，剩下 95% 的时间 GPU 大部分 SM 空闲。**这是 tail effect 的定量描述**，在 `LaunchStats` 里直接给。

**追问：怎么修？** 让 block 数是"每波容量"的整数倍；或者改用 grid-stride loop，把 grid 固定成整数波，每个 block 处理多份工作。
