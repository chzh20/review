# W2 · 内存层级与访存优化

> 一句话总纲：**CUDA 的性能瓶颈 80% 在访存**。这一周的所有题，都是在问"你的访存 pattern 浪费了多少带宽"。

---

## 一、面试官在筛什么

W2 是淘汰率最高的一周。面试官会给你一段代码或一个数据结构，让你判断"快还是慢、为什么、怎么改"，而且不接受"加 cache""用 shared memory"这种没有量化的答案。

他在确认：

1. 你知道**访存的原子单位是 32B sector，不是 4B 变量**。
2. 你知道 **shared memory 的价值不是"更快"，而是"可控的复用 + 把不合并的访问变成合并的"**。
3. 你能**算**——不是感觉，而是报出"浪费了几倍""省了几倍"。

## 二、内存层级

### 2.1 全景表

| 层级 | 物理位置 | 延迟（量级，cycles） | 容量（A100） | 作用域 | 生命周期 | 谁管 |
|---|---|---|---|---|---|---|
| Register | SM 内寄存器堆 | ~1 | 256 KB / SM | 单线程 | kernel | 编译器 |
| **Shared Memory** | SM 内 | **20–30** | 164 KB / SM | **block 内所有线程** | block | **程序员** |
| L1 Cache | SM 内（与 shared 共用 192 KB） | ~30 | 可配 | SM | — | 硬件 |
| L2 Cache | 芯片上 | ~200 | 40 MB | 全设备 | — | 硬件 |
| **Global Memory** | HBM2 | **400–800** | 40/80 GB | 全设备 | 应用 | 程序员 |
| Constant | HBM + 8 KB/SM 常量缓存 | 命中时极快，且**广播免费** | 64 KB | 全设备 | 应用 | 程序员 |
| Local | HBM（走 L1/L2） | 同 global | 每线程 ≤512 KB | 单线程 | kernel | 编译器（溢出） |
| Texture / `__ldg` | HBM + 只读缓存 | 同 global | — | 全设备 | 应用 | 程序员 |

延迟数字为量级参考，实测值随架构与测量方法变化很大 [R11]。**面试时请说"几百个周期"而不是"437 个周期"**——后者一听就是背的。

### 2.2 三个必须想通的问题

**① shared memory 为什么快？**
不是因为它"是 SRAM"。L1 也是 SRAM，但 L1 对程序员不可见、命中率不可控。shared memory 快在三点：
- **显式分配**，不存在 cache miss 的随机性——你写的时候就知道它在。
- **没有 tag 比对和替换逻辑**，直接用索引寻址（bank 并行访问）。
- **带宽高**：32 banks × 4 B / cycle = **128 B/cycle/SM**，A100 @1.41 GHz × 108 SM ≈ 19 TB/s，是 HBM 的 12 倍。

**② local memory 什么时候出现？**
当寄存器不够、数组被动态索引（`a[i]` 且 `i` 由运行时决定）、或结构体太大时，编译器把变量放到 "local" 空间——**它在物理上位于 global memory（HBM），只是逻辑上每线程私有**。所以：**register spill 不是"降到 L2"，是打到显存**。发现方法：`nvcc -Xptxas -v` 看 `spill stores/loads`，或用 NCU 的 `LaunchStats` 看每线程 local memory 字节数。降到 0 的手段是减小 block size 让编译器少用寄存器、`__launch_bounds__`、或把大数组挪到 shared memory。

**③ 什么时候**不该**用 shared memory？**
当数据只被用一次（无复用）时，shared memory 只是多了一步搬运：global → shared → register，还多了一次 `__syncthreads()`。典型反例：element-wise 算子（vector add、ReLU）用 shared memory 只会更慢。**判据是复用次数**：一个数据被 block 内线程用了 ≥2 次才值得进 shared。

## 三、合并访存（Coalesced Access）

### 3.1 硬件怎么合并

一个 warp 的 32 个线程同时发一条 `LDG` 指令，地址生成单元会把这些请求**按 32 字节 sector 归并**，然后是 128 字节的 cache line [R3]。

```
一次 warp 的访存 → 落在几个 128B cache line 上 → 每条 line 拆成 4 个 32B sector
→ 只搬被触碰到的 sector（sector 内的 32 字节全部搬走，哪怕只用了 4 字节）
```

**效率的定义**：`有用字节 / 实际搬运字节`。

### 3.2 三种 pattern 的定量分析（必背）

设 `float a[N]`，warp 内 `lane = 0..31`：

| Pattern | warp 触碰的地址 | 搬运量 | 效率 | 说明 |
|---|---|---|---|---|
| `a[base + lane]` | 连续 128 B | 4 sector = 128 B | **100%** | 完美合并 |
| `a[base + 2*lane]` | 跨 256 B | 8 sector = 256 B | **50%** | 步长 2，官方实测带宽约减半 [R3] |
| `a[base + 32*lane]` | 32 个不同 line | 32 sector = **1024 B** | **12.5%** | 列访问的典型，浪费 8 倍 |
| `a[base + lane*4]`（`float4`） | 512 B | 16 sector = 512 B | **100%** | 向量化，效率不变但**指令数减 4 倍** |

第三行是**矩阵按列访问**的经典灾难：对 `float A[1024][1024]`，`A[k][col]` 且 `col = tid`，一个 warp 的 32 个线程跨了 32 行 = 32 个 128 B 区间，只各取 4 字节。

**面试必答的计算**：
> `stride = 32` 的 float 访问，有效带宽只有峰值的 1/8。A100 的 1555 GB/s 实际只能拿到约 **195 GB/s**。

### 3.3 AOS vs SOA

```cpp
// AOS (Array of Structures) —— 灾难
struct Particle { float x, y, z, vx, vy, vz; };   // 24 B
Particle p[N];
kernel: p[i].x += p[i].vx * dt;                  // 一个 warp 只用到 8/24 字节
                                                  // 效率 33%，另 2/3 带宽白烧

// SOA (Structure of Arrays) —— 正确
float px[N], py[N], pz[N], vx[N], vy[N], vz[N];
kernel: px[i] += vx[i] * dt;                     // 连续访问，100% 效率
```

**标准答法**："AOS 里一个线程需要的字段和相邻线程的字段交错在一起，warp 会把整个结构体的 24 字节全搬进来但只用 8 字节。改成 SOA 后每一个数组都是连续访问，效率 100%。这不是 cache 能救的问题——**cache 救不了带宽浪费，只能救延迟**。"

（如果是 EDA / 物理仿真场景，还要补一句：AOS 在**线程内**访问同一对象的多个字段时反而有局部性优势，当字段数 ≥4 且线程内复用充分时 AOS 可能更优，要看具体 pattern 算。这句话能显示你不是背模板。）

### 3.4 三个立刻能用的优化

```cpp
// 1) __restrict__ + const：让编译器走 LDG.CI（只读数据缓存路径）
__global__ void k(const float* __restrict__ in, float* __restrict__ out, int n);

// 2) 向量化：把 4 次 4B 访存变成 1 次 16B 访存
float4 v = reinterpret_cast<const float4*>(in)[i];

// 3) 让每个线程处理连续的一段，而不是交错的一段（当无法向量化时）
//    交错：i = tid + k*blockDim.x       → 每次 warp 都合并，最佳
//    分块：i = tid*K + k                → warp 内跨 K 个元素，可能不合并
//    优先选交错
```

**注意 `float4` 的前提**：指针必须 **16 字节对齐**（`cudaMalloc` 返回的天然 256B 对齐，没问题；但 `&a[1]` 就不是）。非对齐的 `float4` 访问会触发 misaligned address 错误。

## 四、Shared Memory 与 Bank Conflict

### 4.1 结构

- shared memory 被划分为 **32 个 bank**，每个 bank 宽度 **4 字节**（Volta 之后固定，旧的 8 字节模式已废弃）[R2][R3]。
- 一个 32 位字的 bank 索引：`bank = (word_address) % 32`，其中 `word_address = byte_address / 4`。
- 每周期每个 bank 只能服务**一个** 32 位访问（无 dual-port）。一个 warp 的 32 个线程，如果落在 32 个不同 bank → **1 个周期完成**；如果 k 个线程落同一个 bank 且地址不同 → **k 个周期（k-way conflict）**。

**例外（很重要）**：多个线程访问**同一个地址**不是冲突，而是**广播（broadcast）**，1 个周期完成。这是官方文档明确写的例外 [R3]。

**补充**：Volta 之后还有 **multicast** —— 一个 warp 内多个不同地址但属于同一 32 字节对齐段时，可以合并为一次多播。所以现代 GPU 的 bank conflict 模型比教科书宽松一些，但按经典模型算不会错。

### 4.2 经典案例：32×32 矩阵转置

```cpp
#define BDIM 32

// 版本 A：有 32-way bank conflict
__global__ void transposeConflict(float* out, const float* in, int n) {
    __shared__ float tile[BDIM][BDIM];
    int x = blockIdx.x * BDIM + threadIdx.x;
    int y = blockIdx.y * BDIM + threadIdx.y;
    if (x < n && y < n) tile[threadIdx.y][threadIdx.x] = in[y * n + x];  // 写入：合并 + 无冲突
    __syncthreads();
    x = blockIdx.y * BDIM + threadIdx.x;
    y = blockIdx.x * BDIM + threadIdx.y;
    if (x < n && y < n) out[y * n + x] = tile[threadIdx.x][threadIdx.y]; // 读出：32-way 冲突
}

// 版本 B：padding 后无冲突
__global__ void transposePadded(float* out, const float* in, int n) {
    __shared__ float tile[BDIM][BDIM + 1];   // ← 只改这一个数字
    /* 其余完全相同 */
}
```

**为什么 A 版读出会 32 路冲突？**

一个 warp = `threadIdx.x = 0..31`、`threadIdx.y` 固定。读 `tile[threadIdx.x][threadIdx.y]`：

```
word_addr = threadIdx.x * 32 + threadIdx.y
bank      = (threadIdx.x * 32 + threadIdx.y) % 32 = threadIdx.y   ← 与 threadIdx.x 无关！
```

32 个线程全部落在 **bank `threadIdx.y`** 上，但地址各不相同 → **32-way conflict，串行 32 个周期**。

**为什么 B 版就没了？**

```
word_addr = threadIdx.x * 33 + threadIdx.y
bank      = (threadIdx.x * 33 + threadIdx.y) % 32
          = (threadIdx.x * 32 + threadIdx.x + threadIdx.y) % 32
          = (threadIdx.x + threadIdx.y) % 32      ← 随 threadIdx.x 递增，32 个线程各不相同
```

**数学本质**：bank 索引是地址对 32 取模。`stride = 32` 时模 32 结果恒定，`stride = 32k+1`（与 32 互素）时模 32 结果铺满所有 bank。**所以 padding 的正确量是 +1（导致 stride 与 bank 数互素），不是随便加。**

**追问：能不能不加 padding，改用别的方法？**
能。① 读的时候把 32×32 拆成 4 个 8×8 子块（对应 `float4` 16 字节行），现代做法；② 用 64 位 bank 模式（已废弃）；③ 干脆用 `cuda::memcpy_async` / `cp.async` 走 shared memory 的 bypass 路径。面试时答"padding 是最简单通用的解法，工程上现代 kernel 更常用向量化 + swizzle"是加分项。

**追问：写入那一侧有冲突吗？**
没有。写 `tile[threadIdx.y][threadIdx.x]`：`bank = threadIdx.x % 32`，warp 内各不相同，且 global 侧的 `in[y*n+x]` 是连续的，合并访存。**只有转置读的一侧冲突** —— 这也是为什么"转置"是 bank conflict 的最佳教学案例：它把"合并访存"和"bank conflict"两个问题拧在了一起，解药（padding）只治后者。

### 4.3 其他易踩的坑

| 场景 | 冲突数 | 解法 |
|---|---|---|
| `shared[32][32]` 列访问 | 32-way | padding 到 `[32][33]` |
| `shared[64]` 按 stride 2 访问 | 2-way | 改成 stride 奇数，或重排索引 |
| 结构体数组按字段访问 | 视字段大小 | 拆成 SOA |
| 归约中 `s[tid] += s[tid + offset]` | 无 | bank 与线程一一对应，天然无冲突 |

### 4.4 静态 vs 动态 shared memory

```cpp
__shared__ float s[1024];                    // 静态：编译期确定大小
extern __shared__ float s[];                 // 动态：launch 时传第三个参数
kernel<<<grid, block, 8192>>>(...);          // 8 KB
```

**超过 48 KB 必须用动态分配 + 显式 opt-in**（`cudaFuncSetAttribute(..., cudaFuncAttributeMaxDynamicSharedMemorySize, bytes)`）。A100 上单 block 最多 **163 KB**（每 SM 共 164 KB）[R2]。这是"要 64 KB shared memory 怎么办"的标准答案。

## 五、原子操作

### 5.1 为什么慢

`atomicAdd(&g, v)` 的实现是**在 L2 做的 read-modify-write**：读、加、写三步不可分割，硬件要用锁/归约单元保证原子性。

- **同地址竞争**：N 个线程加同一个地址会被**串行化**成 N 次操作。10 万次 atomic 到同一个 counter，就是 10 万个 L2 往返的排队。
- **不同地址**：一般可以并行，但如果地址落在**同一个 128B line**（false sharing），会互相拖累。

### 5.2 四个优化层次（按效果排序）

```cpp
// ① 树形/共享内存归约：先 block 内聚合，每 block 只发 1 次 atomic  ← 最常用
__shared__ float s[256];
s[tid] = val;
__syncthreads();
/* ... log 步规约 ... */
if (tid == 0) atomicAdd(out, s[0]);

// ② warp 级聚合（sm_80+）：__reduce_add_sync 把 warp 内同值先合并
unsigned mask = __match_any_sync(0xffffffff, value);   // 找出同值的 lane
int leader = __ffs(mask) - 1;
if (lane == leader) atomicAdd(&hist[value], __popc(mask));

// ③ 分桶/打散：histogram 用 shared memory 私有 bin，避免全局竞争
__shared__ unsigned int local[BINS];   // 每 block 一份

// ④ 不返回值的原子：red.global.add 比 atom.global.add 快（不需要回读）
//    返回值没用到时编译器会自动降级为 red，所以别有"我必须要原子返回值"的误解
```

**面试要答出的一句话**："原子的成本不在于指令本身，而在于**同地址的串行化和 L2 往返**。所以优化方向永远是**减少到达全局的原子次数**，而不是换更快的原子指令。"

### 5.3 一个必须知道的坑：`__threadfence()`

`atomicAdd` 保证**这一条操作**的原子性，但不保证**其他内存写的可见顺序**。做"最后一个线程收尾"的经典模式（threadfence reduction）时，必须：

```cpp
// 每个 block 把部分和写进 partial[blockIdx.x]
__threadfence();                                  // 保证写对全 device 可见
if (tid == 0) {
    unsigned int prev = atomicInc(&count, gridDim.x - 1);
    if (prev == gridDim.x - 1) { /* 我是最后一个 block，做最终规约 */ }
}
```
漏掉 `__threadfence()` 会出现"最后一个 block 读到别人没写完的部分和"的间歇性错误——**这种 bug 只在多 block 高负载下复现，是最典型的现场 debug 考题**。

## 七、题库

### Q1. 一个 warp 连续访问 32 个 `float`，产生几次内存事务？

**30 秒答法**：128 字节，正好一条 cache line，拆成 **4 个 32 字节 sector**，属于一次合并访问。搬到 L1 是 1 条 line，实际用满，效率 100%。

**追问：如果起始地址没对齐到 32 字节呢？** 会跨 line，变成 5 个 sector（官方文档给的例子：错位访问需要 5 段而不是 4 段，实测带宽约为对齐时的 9/10，因为有部分 line 复用）[R3]。

**追问：如果访问的是 `double`（8 字节）呢？** 32 × 8 = 256 B = 2 条 line、8 个 sector，仍然是 100% 效率——合并看的是"连续性 + 对齐"，与元素大小无关。

---

### Q2. `A[k][tid]`（列访问）为什么慢 8 倍？

**30 秒答法**：`tid = 0..31` 时地址步长是 `N` 个 float。若 N=1024，相邻线程相隔 4 KB，一个 warp 落在 **32 条不同的 128B line** 上，每条只用到 4 字节，硬件仍要搬 32 B sector → 搬运 32×32 = 1024 B，有效 128 B，**效率 12.5%，浪费 8 倍**。

**追问：怎么改？** 改成行访问（重排循环顺序，让最内层循环走连续维度），或用 shared memory 做 tile 转置——**先把列访问变成"合并的全局读 + 转置在 shared 内完成"**。这正是 tiled GEMM 的核心思想。

**追问：L2 有 40 MB，能不能兜住？** 能缓解但不能解决。L2 命中只是省了 HBM 往返，**sector 级的搬运浪费依然存在**，而且 40 MB 装不下 1024² float（4 MB，其实装得下——所以 N=1024 时 L2 能兜住第二次访问）。诚实答案：**小规模时 L2 会掩盖问题，一旦矩阵超过 L2 容量就暴露，而且即使命中 L2，吞吐也远低于 HBM 峰值**。这个答法会明显高于平均。

---

### Q3. 什么是 Bank Conflict？怎么解决？

**30 秒答法**：shared memory 分 32 个 bank、每 bank 4 字节、每周期每 bank 只能服务一个地址。一个 warp 内若多个线程访问**不同地址但同一 bank**，访问被串行化，n 路冲突就是 n 倍时间。解决：① **padding**，让 stride 与 32 互素（`[32][32]` → `[32][33]`）；② 用向量化访问重排（每线程读 16 B，把 32 路冲突拆成 4 组）；③ 调整数据布局消除列访问。

**追问：同地址也是冲突吗？** 不是，是广播，1 个周期。**这个例外必须提，否则会显得你只背了定义。**

**追问：怎么在运行时确认有冲突？** NCU 的 `Memory Workload Analysis` 里看 `L1 Wavefronts Shared Excessive`（实际 wavefront 数 / 理想数 > 1 就是有冲突），或 `shared_ld_bank_conflict` 相关指标 [R5]。

---

### Q4. 为什么 padding 要加 1，加 2 行不行？

**30 秒答法**：bank 索引 = 地址 mod 32。`[32][32]` 按列访问时，相邻线程地址差 32 个字，mod 32 恒等 → 全撞一个 bank。加 1 后 stride 变 33，`33 mod 32 = 1`，每行错开一个 bank，32 个线程正好铺满 32 个 bank。**加 2 的话 stride=34，`34 mod 32 = 2`，只能铺满 16 个 bank → 变成 2-way conflict**。所以必须加奇数，通常加 1（最省空间）。

**追问：那如果是 `[64][64]` 呢？** 加 1 → stride 65，`65 mod 32 = 1`，同样有效。**规则是 stride 与 32 互素**，不限于 32 的方阵。

---

### Q5. shared memory 和 L1 cache 有什么区别？为什么不用 L1 而用 shared？

**30 秒答法**：物理上是同一块 SRAM（A100 共 192 KB，可切分），但语义完全不同。L1 是**硬件自动管理、对程序员透明、命中率不可控**；shared 是**软件显式分配、生命周期 = block、可以精确控制布局**。用 shared 的理由是：① 需要 **block 内线程共享数据**（L1 没有这个语义保证）；② 需要**可预测的延迟**做流水线；③ 需要**主动把不合并的访问变成合并的**（先把列读进 shared，再从 shared 按行读）。

**追问：shared memory 会占 L1 的空间吗？** 会，它们是同一块物理存储。A100 上 192 KB 的切分由驱动按 kernel 的 shared 申请量自动决定，`cudaFuncAttributePreferredSharedMemoryCarveout` 可以手动调。

---

### Q6. 原子操作为什么慢？十万个线程加一个计数器怎么优化？

**30 秒答法**：全局 atomic 在 L2 做 read-modify-write，同地址会被串行化，十万次就是十万次排队。优化：**先在 block 内用 shared memory 归约，每 block 只发一次 atomic**（十万 → 几百次）；如果还有竞争，用 warp 级聚合（`__match_any_sync` / `__reduce_add_sync`）；再进一步用两阶段归约（partial 数组 + 第二个 kernel）。

**追问：`atomicAdd` 支持 float 吗？** sm_60（Pascal）起有硬件支持；更早的架构是 `atomicCAS` 循环实现（会慢很多）。**double 同样是 sm_60 起**。

**追问：`atomicAdd` 和 `atomicExch` 哪个快？** 一般来说不返回值的操作更快（编译器降级为 `red` 指令）。真正决定速度的是**竞争程度**，不是指令种类。

### Q7. 下面这段 histogram 代码有什么问题？

```cpp
__global__ void hist(const unsigned char* data, int n, unsigned int* out) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) atomicAdd(&out[data[i]], 1u);
}
```
**30 秒答法**：三个问题。① **全局原子竞争**：图像数据通常集中在少数几个灰度值，几十个线程抢同一个 L2 地址；② **grid 太小则覆盖不到 n**（没有 loop）；③ 没有处理 `out` 的初始化（要用 `cudaMemset`）。

正确做法：**每 block 一份 shared memory 私有直方图**（256 bins × 4 B = 1 KB），block 内用 shared atomic，最后每 block 一次性合并到全局。这是把全局竞争降为 block 数级别的标准解法，见 `code/06_histogram.cu`。

### Q8. 什么时候不该用 shared memory？

**30 秒答法**：**没有复用的时候**。shared memory 的价值是"一次搬运、多次使用"。element-wise 类算子（vector add、ReLU、bias add）每个元素只读一次，走 shared 反而多一次搬运 + 一次 `__syncthreads()`，纯亏。判据：**一个数据被 block 内线程使用 ≥2 次才值得**。

**追问：那 vector add 的优化点在哪？** 在**合并访存 + 向量化（`float4`）+ grid-stride loop 减少 launch 开销**，不在 shared memory。这题答"用 shared memory 优化 vector add"是典型的新手错误，面试官一问"复用了几次"就露馅。

---

### Q9. `__syncthreads()` 到底保证什么？

**30 秒答法**：它同时是**执行屏障**和**shared memory 的内存屏障**：block 内所有线程都到达这一点之后才继续，且此前的 shared/global 写对 block 内所有线程可见。它**不能**跨 block 同步，也**不能**替代 `__threadfence()` 的全局可见性语义。

**追问：能不能只在部分线程里调用？** 绝对不能。`__syncthreads()` 必须在 block 内**所有线程都可达**的位置。放在 `if (tid < 128)` 里会导致未定义行为（可能死锁，也可能静默出错）。这是 CUDA 最常见的 bug 之一。

**追问：warp 内需要 sync 吗？** Volta 之后**需要** `__syncwarp()`——因为独立线程调度，warp 内不再有隐式同步保证。

---

### Q10. 什么是 `cp.async`？为什么 Ampere 要加这个指令？

**30 秒答法**：`cp.async`（asynchronous copy）让数据**从 global memory 直接进 shared memory，不经过寄存器**。Ampere 之前的标准做法是 `LDG → 寄存器 → STS`，中间占寄存器、多一条指令、还要等数据到齐。`cp.async` 省掉寄存器中转，且**可以和计算重叠**：发出拷贝后继续算上一块 tile，等 `cp.async.wait_group` 再切 tile。这是 Ampere 上 double-buffered GEMM 的基础，也是 Hopper 上 TMA 的前身 [R15]。

**追问：它和 prefetch 有什么区别？** prefetch 只是提示硬件提前取到 cache，数据还是要经寄存器；`cp.async` 是真正的异步 DMA，落点是 shared memory。
