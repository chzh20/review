# 课程审查与优化报告：对标大模型核心岗位（薪资 ≥60 万/年）

> 审查对象：`llm-inference-course.md`（课程大纲）+ `llm-inference-weekly-plan.md`（20 周逐日计划）
> 审查基准：大模型算法工程师 / AI 应用开发工程师岗位 JD、国内一线大厂与头部 AI 公司 ≥60 万年薪档的能力要求
> 日期：2026-07-27

---

## 〇、执行摘要

**核心结论：现有课程是一门优秀的「推理系统工程师」课程，但不是一门完整的「大模型核心岗位求职」课程。**

- 现有课程在**推理优化**单一维度上深度超标（CUDA/vLLM/性能工程），这一维度在目标岗位能力谱中约占 25–35%。
- 目标岗位能力谱中的**训练/微调、数据、评测、RAG/Agent/Prompt** 五个维度**完全缺失**——这些是算法岗 JD 的硬性要求、应用岗的主要工作内容。
- 求职转化三环节（简历/模拟面试/内推）在现有课程中**零覆盖**。
- 优化方向不是推翻重来，而是：**压缩低求职性价比内容约 4 周 → 新增训练微调与应用链路约 6 周 → 新增求职冲刺 2 周**，总周期从 20 周调整为 **24 周**（每天 2h，共约 336 小时）。

**关于薪资目标的定位说明（重要前提）**：≥60 万/年在国内对应的是一线大厂/头部 AI 公司的**中级偏上**岗位（非应届/初级）。这意味着面试考察重点是「系统理解 + 实战深度 + 工程判断力」，而非八股背诵。现有课程培养的"能读 vLLM 源码、能手写 CUDA kernel"正是这一档位的差异化优势，应保留为核心卖点。

## 一、效率优先：冗余识别与精简建议

### 1.1 审查方法

以「求职边际价值」为唯一标准给每项内容打分：
**A** = 面试高频 + 工作中天天用；**B** = 面试偶考或显著提升工程深度；**C** = 对目标岗位价值低。

### 1.2 逐项审查结果

| # | 现有内容 | 评级 | 处置 | 理由 |
|---|----------|------|------|------|
| 1 | W1–W3 Python 工程化（packaging/pytest/类型系统/asyncio） | **A** | **保留** | 应用岗日常全部用到；工程素养是 ≥60 万档与初级岗的分水岭；CI/测试在简历上是可验证的硬产出 |
| 2 | W4 CPython 源码选读（dictobject.c / ceval_gil.c / typeobject.c） | **C** | **砍除**（改为选读材料） | 面试几乎不问 CPython 实现细节；2 周中约 2 天的高时间成本；GIL 语义在 W3 已覆盖，足够应对面试 |
| 3 | W4 descriptor/metaclass/`__setattr__` 机制 | **B** | **压缩**（4 天 → 1 天） | 只需理解到"能读懂 `nn.Module.__setattr__`"的程度，手写迷你 Module 系统保留（面试可讲），metaclass 插件系统删除——面试与工作都极少用到 |
| 4 | W5–W7 PyTorch + 手写 attention + KV cache | **A** | **保留并加强** | Transformer 细节是所有 LLM 面试的第一道题；RoPE/GQA 已覆盖是加分项；此处应**补充** MoE、RMSNorm、SwiGLU（现代模型标配，面试高频） |
| 5 | W8 推理性能模型（roofline/TTFT/TPOT） | **A** | **保留** | 推理岗必考，算法岗也常考"为什么 decode 是 memory-bound"；一周成本低、回报高 |
| 6 | W9–W10 调度 + PagedAttention + vLLM 导航 | **A** | **保留** | vLLM 是两个岗位共同的部署/推理事实标准；论文精读产出可直接写进简历 |
| 7 | W11 CPU 性能工程（false sharing/分支预测/perf） | **C** | **大幅压缩**（1 周 → 2 天，并入 W12） | 目标岗位面试不考 CPU cache 细节；唯一价值是建立性能直觉，2 天实验足够 |
| 8 | W12 CPU GEMM 优化专项（AVX2/OpenMP） | **C+** | **压缩为选做**（1 周 → 挑战项） | CPU GEMM 优化是推理引擎岗的内容，对算法/应用岗边际价值低；保留 tiling 思想讲解（为 CUDA 铺垫），删除 AVX2 intrinsics 手写要求 |
| 9 | W13 pybind11 + torch.ops 扩展 | **B** | **保留但压缩**（1 周 → 4 天） | 是"算法 + 工程"复合能力的证明，简历加分；但 TORCH_LIBRARY 注册细节可降低要求 |
| 10 | W14–W17 CUDA（含 paged attention kernel） | **B+** | **保留，允许分流** | 对算法岗是强加分项（懂 kernel 的算法工程师稀缺）；对应用岗价值中等。**优化：设为"系统方向"选修轨道**，应用方向学员可用 Triton 替代手写 CUDA（W17 已有雏形） |
| 11 | W18–W19 三层源码对照 + vLLM 深水区 | **A**（系统方向）/ **B**（应用方向） | **保留，深度分流** | 系统方向全文精读；应用方向只保留 W18 三层对照（建立全局图），W19 深水区改为选读 |
| 12 | W20 最终集成与验收实验 | **A** | **保留** | mini-infer 是作品集核心项目，验收实验数据是简历量化素材 |

### 1.3 精简汇总

| 处置 | 内容 | 释放时间 |
|------|------|----------|
| 砍除 | CPython 源码选读、metaclass 插件系统、AVX2 手写 | ≈ 1.5 周 |
| 压缩 | W4 高阶机制、W11 CPU 性能、W13 扩展注册细节 | ≈ 1.5 周 |
| 分流 | CUDA/vLLM 深水区按方向选修 | 应用方向再省 ≈ 2 周 |

**合计释放约 3 周**（应用方向 5 周），全部重新分配给第六、七节的新增模块。
**理由**：释放的均是"对推理引擎岗重要、对目标岗位边际价值低"的内容；保留项覆盖两个岗位 JD 的交集主干。

### 2.3 缺口结论

现有课程覆盖了两个岗位 JD 交集的「推理 + 工程」主干（约 35%），但：
- **算法岗 5 个硬性要求全部缺失**（预训练、微调、分布式、数据、评测）；
- **应用岗 4 个日常工作内容全部缺失**（RAG、Agent、Prompt、应用评测）。

**理由**：这两类岗位招聘时的简历筛选关键词就是上表左列；缺任何一行，简历关即被过滤。推理优化再深也无法补偿——它是加分项不是入场券。

## 三、实战闭环：链路覆盖审查与项目改造

### 3.1 完整链路覆盖现状

| 链路环节 | 现有项目覆盖 | 判定 |
|----------|--------------|------|
| 训练 | ❌ 无 | 断链 |
| 微调 | ❌ 无 | 断链 |
| 推理优化 | ✅ mini-infer（v0.1→v1.0） | 闭环，质量高 |
| RAG 架构 | ❌ 无 | 断链 |
| Prompt 工程 | ❌ 无 | 断链 |

**结论：5 环链路断了 4 环。** 现有项目单点极深，但无法向招聘方证明"端到端交付能力"。

### 3.2 新增/改造项目设计（每个项目均按「作品集标准」验收）

**作品集统一标准**（理由：招聘方看作品集只看 5 样东西，缺一不可）：
① README 含问题定义与方案取舍；② 可一键复现（脚本/依赖锁定）；③ 量化结果（指标/曲线/对照实验）；④ 一篇技术拆解文章；⑤ GitHub 公开 + commit 历史体现真实开发过程。

| 项目 | 覆盖环节 | 内容 | 关键产出（简历素材） |
|------|----------|------|----------------------|
| **P1 迷你预训练**（新增，2 周） | 训练 | nanoGPT 级复现：从零训练一个小模型（中文小语料），含数据清洗/分词训练/训练曲线分析 | "从零实现并训练 XX 参数模型，验证 loss 下降与 Scaling 规律"；wandb 曲线截图 |
| **P2 领域微调**（新增，2 周） | 微调 | LoRA/QLoRA 对一个 7B 级开源模型做领域 SFT（自选垂直领域），含数据构造、训练、评测对比；DPO 跑通一个偏好对齐小实验 | "用 QLoRA 在单卡完成 7B 领域微调，XX 评测集提升 X 个点"；超参对照表 |
| **P3 mini-infer**（现有，保留） | 推理优化 | 不变；验收时要求**用 P2 微调出的模型做推理**，形成 P2→P3 串联 | 现有三组实验 + "支撑自研微调模型的高效推理" |
| **P4 生产级 RAG**（新增，2.5 周） | RAG + Prompt | 端到端：文档解析→chunking 策略实验→embedding 选型→向量库→混合检索（BM25+向量）→rerank→生成；Prompt 模板版本化 + 评测驱动迭代；用 vLLM 部署生成模型 | "构建 XX 领域 RAG，检索命中率/答案正确率 XX，延迟 XX ms"；chunking 对照实验数据 |
| **P5 Agent 应用**（新增，1.5 周） | Agent + Prompt | function calling + MCP 工具集成的任务型 Agent（如数据分析助手）；含规划、工具调用、错误恢复 | "实现支持 N 种工具的 Agent，任务完成率 XX" |
| **P6 评测体系**（新增，贯穿） | 评测 | 为 P2/P4/P5 各建评测集与自动化评估流水线，接入 CI 回归 | "建立 X 个评测集共 N 条 case，评估流水线接入 CI" |

**闭环验证**：P1（训出基座认知）→ P2（微调出领域模型）→ P3（自研引擎跑推理）→ P4/P5（模型接入真实应用）→ P6（全链路质量保障）。五个项目合起来就是简历的「项目经历」主体。

## 四、求职转化：三环节落地方案

**现状评估：现有课程对三个环节零覆盖，必须新增独立模块（M7，2 周 + 全程伴随任务）。**

### 4.1 简历优化

| 措施 | 具体执行 | 落地性评估与理由 |
|------|----------|------------------|
| 伴随式简历更新 | 从 M1 起，每个模块结束**当周必须更新一次简历**（把模块成果写成 1–2 条量化 bullet）；禁止课程结束后一次性补写 | 高。理由：趁热写成本最低；且每条 bullet 都源自刚验收的实验数据，杜绝编造 |
| bullet 公式 | 「动作 + 技术栈 + 量化结果」：如"实现 continuous batching 调度器，短请求等待降低 XX%（N 组对照实验）" | 高。理由：HR/面试官筛选简历时量化结果的通过率显著高于职责描述 |
| 作品集矩阵 | 简历只放 3 个项目（按目标岗位选：算法岗 = P1+P2+P3；应用岗 = P3+P4+P5），其余进 GitHub pinned | 高。理由：简历信息密度原则；项目方向与岗位错配是常见被拒原因 |
| 双版本简历 | 算法岗版（突出训练/微调/论文复现）与应用岗版（突出工程/RAG/部署）分别维护 | 高。理由：两类 JD 关键词不同，一稿多投通过率低 |

### 4.2 模拟面试

| 措施 | 具体执行 | 落地性评估与理由 |
|------|----------|------------------|
| 八股题库自测（贯穿） | 从 W6 起每周日 30 分钟：本周主题的高频面试题自答录音并回听（题库按模块维护在 `docs/interview-qa/`） | 高。理由：零成本、可自我执行；录音回听暴露"以为懂但讲不清"的问题——这是 ≥60 万档面试的主要挂点 |
| 高频题清单（按模块） | Transformer 细节（W6）/ KV cache 与推理优化（W8–10）/ LoRA 原理与超参（M3.5b）/ RLHF vs DPO（M3.5b）/ RAG 调优链路（M5.5a）/ 评测方法（M5.5c） | 高。理由：均为各厂公开面经中的复现题 |
| 项目深挖演练 | 每个作品集项目准备「5 层 why」问答：为什么选这个方案→trade-off 是什么→指标怎么定义→遇到的最大坑→如果重做怎么改 | 高。理由：中高级岗位面试 60% 时间在深挖项目；课程内每个项目本来就要求写取舍文档，直接转化 |
| 编码/手撕题 | 每周 2 题 LeetCode（hot 100 范围，从 M1 起）；M5 期间加手撕 attention/softmax kernel 练习（面试实拍题） | 高。理由：算法岗笔试硬门槛；手撕 attention 是大模型岗真实高频题 |
| 全真模拟（M7） | 第 23–24 周：≥3 轮完整模拟（自我介绍 3min + 项目深挖 40min + 八股 20min + 编码 45min），找同行/朋友/付费平台（如牛客模拟面）执行 | 中。理由：付费平台或同行互面都可获得；关键是**必须真人**，自练无法模拟追问压力 |
| 系统设计专项 | 准备 2 道题："设计一个 LLM 推理服务"（直接复用 mini-infer 架构图）和"设计一个企业知识库问答系统"（复用 RAG 项目） | 高。理由：应用岗系统设计题几乎必考，且答案就在作品集里 |

### 4.3 内推资源

**坦诚评估：这是三环节中落地确定性最低的，课程无法"提供"内推，只能系统性提高获得内推的概率。**

| 措施 | 具体执行 | 落地性评估与理由 |
|------|----------|------------------|
| 开源贡献作敲门砖 | M5/W17 的挑战项升级为**强制**：给 vLLM/llama.cpp/SGLang 提 ≥1 个文档/测试/小修复 PR；P1–P5 期间再争取 1 个 | 中高。理由：文档/测试类 PR 门槛低、周期短；merged PR 是简历上与目标公司工程师建立连接的最短路径，且 PR review 过程本身就是弱关系内推渠道 |
| 技术内容输出 | 每个项目配套的技术拆解文章公开发布（知乎/掘金/个人博客），全程 ≥6 篇 | 中高。理由：持续输出是国内获得内推私信的最常见路径之一；面试官面试前搜到候选人的深度文章会显著提高评价起点 |
| 社区参与 | 加入 2–3 个目标公司技术社区/开源社区（vLLM 社区、各厂大模型团队的技术公众号/Meetup）；每季度至少 1 次公开提问/分享 | 中。理由：转化率低但成本也低；Meetup 线下是获取内推的高效场景 |
| 人脉盘点与激活 | M7 第 1 周：列出目标公司清单（10–15 家），逐一标注可触达路径（前同事/校友/开源社区/猎头）；对弱关系发送基于作品的触达消息（附 GitHub/文章，不空口求内推） | 中。理由：这是可执行但依赖个人既有积累的动作；课程能做的是把"触达时的弹药"（作品集+文章+PR）准备好 |
| 猎头渠道 | M7 注册 2–3 个专注 AI 的猎头渠道；简历关键词按 JD 优化（LLM/RAG/vLLM/LoRA 必须出现在技能区） | 中高。理由：≥60 万档岗位大量经猎头流转；关键词优化直接决定被检索到的概率 |

### 5.3 与原 20 周计划的差异对照

### 5.4 方向分流说明

- **算法岗方向**：W16–18 走完整 CUDA 轨道；W22 读 vLLM 深水区；简历项目 = P1+P2+P3。
- **应用岗方向**：W17–18 改 Triton 轨道（省约 1 周，可提前进入 W19）；W22 只读三层对照；简历项目 = P3+P4+P5。
- 两方向共享 W1–15 与 W19–21——这是 JD 交集，不可省略。

## 六、风险与诚实的保留意见

1. **24 周 × 2h/天是下限而非保证**：≥60 万档岗位竞争激烈，课程提供能力路径，但学历背景、过往公司、工作年限等硬条件不在课程控制范围内。若硬条件偏弱，开源贡献与技术输出的权重需进一步提高。
2. **训练模块受算力约束**：P1 用单卡小模型可控；P2 的 7B QLoRA 需 24GB 级显存（可租 AutoDL/云 GPU，全程预算约数百元），无 GPU 时可用更小模型（1.5B）降级，但简历表述需相应调整。
3. **内推环节不可承诺**：§4.3 已如实标注各措施确定性；课程负责"弹药"，触达动作依赖个人执行。
4. **不要被新项目拖垮主线**：P1/P2/P4/P5 严格限时（超时就缩小数据规模/领域范围），作品集"完成且可讲"优先于"大而全"。
