🏗️vLLM 架构与请求数据流

请求从客户端到 GPU 执行经过五个核心组件。理解这条数据流是后续源码追踪的基础。

数据流五步骤详解
  1. Client → API Server：HTTP 请求（/v1/completions 或 /v1/chat/completions），或 Python SDK 离线调用
  2. API Server → Engine：请求封装为 SequenceGroup，加入 waiting queue
  3. Scheduler ↔ Block Manager：每个 scheduling step，Scheduler 从 waiting/running 队列选 batch，向 Block Manager 查询/分配物理块。显存不足时可抢占（preempt）低优先级请求，将 KV Cache 换出到 CPU
  4. Scheduler → Worker：选定 batch 传给 Worker，Worker 在 GPU 上执行 model forward（prefill 或 decode）
  5. Worker ↔ GPU Memory：Worker 通过 Block Table 获取 KV Cache 物理块位置，PagedAttention kernel 根据映射表散列读取 KV

D1
在自回归生成（autoregressive generation）中，模型每生成一个 token 需要做什么计算？为什么不能像 BERT 那样一次前向传播输出全部结果？
讲解

自回归生成的本质：模型每次只输出 1 个 token，然后把它拼回输入序列，再进行下一次前向传播。循环往复，直到遇到结束符。

为什么不能像 BERT 一次出结果？

  • BERT 是双向注意力 + 完形填空（已知位置填空），输入中所有 token 同时可见，可以一次算完
  • GPT 类模型是因果生成（causal generation）——第 N 个 token 依赖第 N-1 个 token 的输出。你不知道第 N 个 token 是什么，就没法算第 N+1 个
  • 这种依赖关系是串行的，无法并行化

关键后果：生成长度为 L 的文本需要做 L 次前向传播，这是 LLM 推理慢的根本原因。每次前向传播的输入序列都比上一次多 1 个 token。

核心要点：自回归 = 串行生成，每步依赖上一步输出，L 次前向传播不可避免

D2
假设一个 7B 参数模型，FP16 精度。模型权重本身需要多少显存？如果同时服务 100 个并发请求，每个请求平均 2048 token 上下文，KV Cache 大约需要多少显存？（不需要精确，给出数量级和计算思路即可）
讲解

模型权重：7B 参数 × 2 bytes（FP16）= ~14 GB。这是固定开销，不随请求数变化。

KV Cache：公式是 2 × n_layers × n_heads × d_head × seq_len × batch × 2 bytes

以 Llama-2 7B 为例（n_layers=32, n_heads=32, d_head=128, seq_len=2048, batch=100）：

2 × 32 × 32 × 128 × 2048 × 100 × 2 = 13.1 GB

总计 ≈ 27 GB（A100 80GB 还剩 53GB 可用）

核心洞察：KV Cache 随并发数线性增长，这才是真正需要优化的瓶颈，而非模型权重

D3
在 LLM serving 中，"prefill" 和 "decode" 两个阶段的计算特征有什么本质区别？这对 batching 策略有什么影响？
讲解

Prefill 阶段（处理 prompt）：一次处理几百个 token，是矩阵×矩阵运算（GEMM），计算密集，GPU 利用率高（>80%）

Decode 阶段（逐个生成）：每次只处理 1 个 token，是矩阵×向量运算（GEMV），访存密集，GPU 利用率不到 1%

算术强度差距 ~800 倍：Prefill 每读 1 byte 权重能做 ~800 次浮点运算，Decode 只能做 ~1 次

对 batching 策略的影响：

  • Prefill 不需要太大 batch 就能打满 GPU，但会阻塞正在 decode 的请求
  • Decode 单请求严重浪费 GPU，必须把很多请求打包在一起分摊访存开销
  • 这就是 Continuous Batching 的动机——动态混合 prefill 和 decode 请求

核心要点：Prefill 是计算密集（GPU 高效），Decode 是访存密集（GPU 浪费），两者需要不同的调度策略

D6
Continuous batching（连续批处理）与传统的 static batching 有什么区别？为什么传统 batching 在 LLM serving 中效率低？
讲解

Static Batching：把多个请求打包成一批，必须等所有请求都生成完才能开始下一批。短请求被长请求拖累，GPU 空等。

Continuous Batching：每个 decode step（每生成一个 token）都可以动态加入新请求、移除已完成请求，GPU 几乎不空闲。

为什么传统 batching 在 LLM serving 中效率低？

  • LLM 生成长度不可预测——请求 A 可能 50 token 就结束，请求 B 可能要 500 token
  • Static batching 让短请求白等长请求，GPU 大量空闲
  • 每个 decode step 是独立的（只处理 1 个 token），天然适合动态加入/移除请求
  • 配合 PagedAttention，KV Cache 可以在请求加入/离开时轻松管理

核心要点：Continuous Batching = 工厂流水线动态调度，不让任何工位空闲

D8
在实际部署 LLM 时，吞吐量（throughput）和延迟（latency）之间需要做哪些权衡？哪些因素影响这个权衡？
讲解

吞吐量（每秒处理多少请求）和延迟（单个请求等多久）天然矛盾——batch size 越大吞吐越高，但每个请求排队时间也越长。

不同场景需要不同策略：

  • 实时对话（ChatGPT 式）：低延迟优先，batch=1~8，牺牲吞吐量
  • 批量处理（文档摘要、数据标注）：高吞吐优先，batch=64~256+，容忍高延迟

影响权衡的因素：

  • Batch size 越大 → 吞吐越高，但每个请求排队等越久
  • 模型越大 → 单请求计算越久，延迟越高
  • Prefill 和 Decode 分离调度 → 可以兼顾两者

vLLM 的优势：Continuous Batching 让系统可以在两个极端之间动态调整，而不是固定在某个 batch size。

核心要点：吞吐和延迟天然矛盾，需要根据应用场景选择合适的操作点

💡核心解释

4.1 LLM serving 的真正瓶颈

很多人说"LLM 推理慢"。但精确地说，瓶颈不是"计算慢"，而是显存管理低效导致并发不足。

自回归生成的本质：每生成一个 token，都需要用到之前所有 token 的 K 和 V（合称 KV Cache）。这意味着：

  • 显存占用随序列长度线性增长：一个 7B 模型，单条 2048 token 的请求，KV Cache 约占 1-2 GB
  • 显存占用随并发数线性增长：100 个并发请求 → 100-200 GB KV Cache
  • KV Cache 的生命周期与请求绑定：请求结束才能释放

关键矛盾：GPU 的计算能力（FLOPS）往往不是瓶颈——显存容量和显存带宽才是。一个 7B 模型在 A100 上，单次 decode 的计算量很小（GEMV），但要把 KV Cache 从显存读到 SM（Streaming Multiprocessor）上执行 attention，访存开销远大于计算开销。

核心问题定义：LLM serving 的核心问题 = 在有限显存内，最大化并发请求数，同时保持低延迟。

4.2 vLLM 的三个核心设计决策

机制解决的问题一句话原理类比
PagedAttention KV Cache 的显存碎片 将 KV Cache 分成固定大小的块（block），按需分配，用 Block Table 做逻辑→物理映射 OS 虚拟内存分页
Continuous Batching 请求长度不齐导致 GPU 空闲 每个 decode step 都重新组 batch：完成的请求移出、新请求加入 流水线 vs 批处理
Prefix Caching 相同前缀重复计算 检测多个请求共享的 prompt 前缀，复用其 KV Cache HTTP 响应缓存

4.3 不使用这些机制时的后果

不用 PagedAttention

为每个请求预分配最大序列长度的连续 KV Cache。如果 max_seq_len=2048，但请求实际只用了 200 tokens，那么 90% 的预留显存被浪费。更严重的是，当请求完成释放后，留下的碎片无法被新请求使用（外部碎片）。

不用 Continuous Batching

一个 batch 内的请求必须等最长的那个完成才能整体释放。如果有 8 个请求，7 个在 50 tokens 时就完成了，但第 8 个要生成 500 tokens，那么前 7 个请求的 KV Cache 空间白白占着 450 步。

不用 Prefix Caching

100 个用户问"请帮我翻译以下文本"，每次都要重新计算相同的 system prompt 的 KV Cache，浪费大量 prefill 计算。

🔄请求流程与架构关系

见上方架构图。数据流的五个步骤已在架构图下方详解。核心要点：

  • Scheduler 是整个系统的"大脑"，每个 step 做三件事：从 waiting 选 prefill、从 running 选 decode、向 Block Manager 请求分配块
  • Block Manager 维护逻辑→物理块的映射表（Block Table），类似 OS 的页表
  • Worker 执行实际的 GPU 计算：prefill 一次性算所有 prompt KV，decode 每步生成 1 token 追加到 KV Cache
  • 生成的 token 通过 Streamer 返回 API Server，再返回 Client

📝最小示例

一个请求从发起到返回的最小流程（伪代码，展示概念而非可运行代码）：

# === 用户视角 ===
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="dummy")
response = client.completions.create(
    model="meta-llama/Llama-2-7b-hf",
    prompt="解释什么是虚拟内存",
    max_tokens=100,
)
print(response.choices[0].text)

# === vLLM 内部（概念性伪代码）===
# 1. API Server 接收请求，创建 SequenceGroup
seq_group = SequenceGroup(prompt="解释什么是虚拟内存", max_tokens=100)

# 2. Engine 将请求加入 waiting 队列
engine.scheduler.waiting.append(seq_group)

# 3. Scheduler 每个 step 做决策:
#    - 从 waiting 中选请求做 prefill
#    - 从 running 中选请求做 decode
#    - 向 BlockManager 请求分配块
scheduled = scheduler.schedule()  # 返回 ScheduledSequenceGroups

# 4. Worker 执行:
#    - prefill: 一次性计算 prompt 的所有 KV
#    - decode: 每步生成 1 token, 追加到 KV Cache
output = worker.execute_model(scheduled)

# 5. 生成的 token 通过 Streamer 返回给 API Server → Client

⚠️常见误区

误区修正
"vLLM 让推理变快了" vLLM 提升的是吞吐量（单位时间处理的请求数），不一定是单请求延迟。单请求延迟甚至可能略增（调度开销）
"PagedAttention 就是分页" PagedAttention 的核心不仅是分页，还包括 Block Table 的逻辑→物理映射和非连续 KV 的 attention kernel 重写。没有后者，分页只是数据结构，无法执行
"vLLM 适合所有 LLM 部署" 小模型（<1B）、单用户场景、需要极致单请求延迟的场景，vLLM 的开销可能不划算
"KV Cache 占用的是模型权重显存" KV Cache 是运行时分配的动态显存，与模型权重（静态显存）独立。GPU 显存 = 权重 + KV Cache + 激活值
"Continuous batching 就是动态 batch" Continuous batching 的关键是 iteration-level scheduling：每个 decode step 都可以改变 batch 组成，而不是 request-level 的动态 batch

🔄自回归生成的本质

什么是自回归生成

自回归（Autoregressive）生成的核心特征：每次只生成一个 token，且每一步都依赖之前所有 token 的信息。这与 BERT 等编码器模型有本质区别——BERT 可以一次处理整个输入序列，而 GPT 类模型必须逐 token 生成。

为什么不能并行生成

在自回归生成中，第 t 步的输出是第 t+1 步的输入。你必须知道第 t 步生成的是什么 token，才能计算第 t+1 步的 Q（Query），进而通过 attention 从历史 KV 中检索信息。

这是数据依赖，不是工程限制——没有投机解码（speculative decoding）等技术的话，这个依赖是不可打破的。

Prefill 例外：Prompt 部分的所有 token 是已知的，可以一次性前向传播计算所有 token 的 K、V、Q——这就是 prefill 阶段。Prefill 一次性处理 S 个 token，计算量是 O(S²)，而 decode 每步处理 1 个 token，计算量是 O(S)。这个差异决定了它们的计算特征完全不同。

💾KV Cache 机制详解

什么是 KV Cache

在 Transformer 的 Self-Attention 中，每个 token 生成三个向量：Q（Query）、K（Key）、V（Value）。Attention 的计算是：

Attention 公式
Attention(Q, K, V) = softmax(Q × KT / √d) × V

在自回归生成中，已有 token 的 K 和 V 在后续步骤中不会变化——因为它们只依赖于该 token 自身和模型权重。因此，可以将每一步计算出的 K 和 V 缓存起来，后续步骤只需读取缓存，避免重复计算。

为什么只缓存 K 和 V，不缓存 Q？因为每一步只有最新生成的 1 个 token需要计算 Q 并参与 attention。历史 token 的 Q 在当前步骤不需要——attention 是"新 Q 查历史 KV"，不是"历史 Q 查历史 KV"。

KV Cache 的生命周期

  1. Prefill 阶段：一次性计算 prompt 中所有 token 的 K 和 V，写入 KV Cache
  2. Decode 阶段：每步只计算 1 个新 token 的 Q、K、V。新 K/V 追加到 Cache，然后用新 Q 对 Cache 中所有 K/V 执行 attention
  3. 请求结束：KV Cache 被释放（在 vLLM 中，物理块归还给 Block Manager）

⚖️Prefill vs Decode：计算特征对比

Prefill 和 Decode 是 LLM 推理的两个阶段，它们的计算特征截然不同。理解这个差异是理解 vLLM 调度策略的基础。

🔵 Prefill 阶段

输入：Prompt 的全部 S 个 token

计算：一次性计算所有 token 的 Q、K、V

Attention：S×S 矩阵（每个 token 与所有 token 做 attention）

FLOPs：O(S² × H × D) — 与序列长度的平方成正比

访存：主要是读模型权重（固定成本）

算术强度：高（大量计算分摊权重读取）

瓶颈：GPU 计算力（compute-bound）

GPU 效率：接近 100%

类比：矩阵乘法（GEMM）

🟠 Decode 阶段

输入：1 个新 token

计算：只计算新 token 的 Q、K、V

Attention：1×S 向量×矩阵（新 Q 对所有历史 KV）

FLOPs：O(S × H × D) — 与序列长度成正比

访存：读全部 KV Cache + 读模型权重

算术强度：极低（少量计算，大量访存）

瓶颈：显存带宽（memory-bound）

GPU 效率：< 1%（batch=1 时）

类比：矩阵-向量乘法（GEMV）

核心差异：算术强度（Arithmetic Intensity）

算术强度 = FLOPs / Bytes（每字节访存执行多少次浮点运算）。它是判断计算密集型还是访存密集型的关键指标。

实验 02 验证的数据（Llama-2-7B, seq_len=1024, batch=1）：
  • Prefill 算术强度 = 808.7 FLOPs/byte（计算密集型，充分利用 GPU）
  • Decode 算术强度 = 1.0 FLOPs/byte（访存密集型，GPU 严重闲置）
  • 差距：809 倍！这就是为什么 decode 是 LLM serving 的性能瓶颈

为什么 Decode 的算术强度这么低？

根本原因：权重读取是固定成本，但 decode 只处理 1 个 token

每次 forward pass，无论 batch size 多少，都需要把模型所有权重从显存读到 SM 上。对于 Llama-2-7B（32 层），权重总量约 12.5 GB。

  • Prefill：读 12.5 GB 权重，处理 1024 个 token → 大量 FLOPs → 高算术强度
  • Decode batch=1：读 12.5 GB 权重，只处理 1 个 token → 极少 FLOPs → 极低算术强度
  • Decode batch=64：读 12.5 GB 权重，处理 64 个 token → FLOPs 增加 64 倍但权重读取不变 → 算术强度提升

🔀Batching 对 Prefill 和 Decode 的不同意义

Prefill Batching

Prefill 已经是计算密集型，GPU 效率接近 100%。增加 prefill batch size 可以提升吞吐量（更多请求并行处理），但不会提升单请求延迟。实际上，大 batch prefill 的单请求延迟可能略增（GPU 算力被分摊）。

策略：在显存允许的范围内，尽可能多地打包 prefill 请求。但注意 prefill 的 KV Cache 写入量 = O(batch × seq_len)，大 batch prefill 会瞬间占用大量显存。

Decode Batching

Decode 是访存密集型，batch=1 时 GPU 效率 < 1%。增加 decode batch size 可以摊薄权重读取成本——多个请求共享同一份模型权重的读取，从而提升 GPU 效率和吞吐量。

策略：尽可能多地打包 decode 请求。这正是 Continuous Batching 的核心——每个 decode step 都可以动态加入新请求、移除已完成请求，最大化 decode batch size。

为什么不能简单地同时做 prefill 和 decode？因为它们的计算特征不同——prefill 是 compute-bound，decode 是 memory-bound。混合在一起会导致 GPU 在两种模式之间切换，降低效率。vLLM 默认使用 prefill-priority 调度：优先处理 prefill 请求，然后在剩余资源中处理 decode。一些版本支持 chunked prefill，将长 prompt 的 prefill 拆分成多个 chunk 与 decode 混合执行。

⚠️常见误区

误区修正
"LLM 推理慢是因为计算量大" Decode 阶段的计算量很小（GEMV），瓶颈是显存带宽——需要把 KV Cache 和模型权重从显存读到 SM，这个传输过程远慢于计算
"KV Cache 和模型权重共用显存" KV Cache 是运行时动态分配的显存，与模型权重（静态加载）独立。GPU 显存 = 权重 + KV Cache + 激活值 + 临时缓冲
"Q 也应该缓存" 不需要。每步 decode 只需要新 token 的 Q去查询历史 KV。历史 token 的 Q 在当前步骤无用——attention 是"新 Q 查历史 KV"
"GQA 只是减少 KV Cache，不影响推理质量" GQA 在减少 KV Cache 的同时可能影响模型质量。Llama-2-70B 用 8 个 KV 头是在质量和效率之间的权衡，不是"免费午餐"
"增加 batch size 总能提升性能" 增加 decode batch size 提升的是吞吐量，不是单请求延迟。而且 batch 越大，KV Cache 占用越多，可能触发 OOM 或 preemption
"Prefill 和 Decode 可以随意混合" 它们的计算特征完全不同（compute-bound vs memory-bound）。混合执行需要专门的策略（如 chunked prefill），否则效率下降
"算术强度高就一定快" 算术强度高意味着 GPU 利用率高，但绝对延迟还取决于总计算量和总访存量。大 batch prefill 算术强度高，但总时间可能更长

⚔️对抗性审查

质疑 1：算术强度计算是否准确？

实验中的 FLOPs 和访存计算基于理论估算，没有考虑 GPU 的内存层次结构（L1/L2 cache、register reuse）。真实的 attention kernel（如 FlashAttention）通过 tiling 和 recomputation 大幅减少了实际显存访问量。实验中 prefill 的算术强度 808.7 可能被高估。

对比 FlashAttention 论文中的实际访存数据，或使用 NVIDIA Nsight Compute 测量真实访存量
质疑 2：GPU 效率 0.2% 是否有误导性？

"batch=1 decode 效率 0.2%"这个数字基于理论峰值算力。真实场景中，GPU 有 L2 cache、tensor core 流水线等优化，实际效率可能更高（虽然仍然很低）。将理论值当实际值报告可能夸大问题严重性。

使用 vLLM 的 benchmark 脚本测量真实的 tokens/s，与理论值对比
质疑 3：权重读取"固定成本"是否完全正确？

"权重读取量不随 batch 变化"这个说法假设 GPU 每次都从 HBM 读全部权重。实际上，GPU L2 cache 可以缓存部分权重，多次 forward pass 之间可能有 cache hit。此外，CUDA kernel 的 tiling 策略会影响实际读取模式。

查阅 GPU L2 cache 大小与模型权重大小的比值，分析 cache hit 率
质疑 4：是否忽略了 MQA（Multi-Query Attention）？

实验对比了 MHA 和 GQA，但没有提及 MQA（所有 Q 头共享 1 个 KV 头）。MQA 比 GQA 更激进，KV Cache 更小，但质量损失也更大。实验和文档没有覆盖这个维度。

补充 MQA 的 KV Cache 计算和典型模型（如 Falcon、PaLM）
质疑 5：Roofline 模型是否过于简化？

Roofline 模型只考虑了峰值 FLOPS 和显存带宽，忽略了 latency bound（访存延迟而非带宽的限制）、kernel launch overhead、CPU-GPU 同步等。对于 decode batch=1，latency bound 可能比 bandwidth bound 更严重。

使用 roofline-with-latency 模型或实际 benchmark 数据修正
质疑 6：KV Cache 公式是否适用于所有模型？

公式 2×L×S×H_kv×D×P×B 假设标准 MHA/GQA 结构。但有些模型使用 sliding window attention（如 Mistral），不需要缓存全部历史 KV。实验中没有区分这个情况。
